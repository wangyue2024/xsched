# 05 下一步论点：从"2.5 段"到论文快路径，先补哪一段？

> 日期：2026-10-27　事实基线：`FINDINGS_ZH.md` §1–§54（2026-10-27）
> 前置：`report/02`（入口证据）、`report/03`（结论 1）、`report/04`（GDB/0317 替代）、`report/kb/ABI.md`（trap/driver ABI）
> 本文不是复现声明，而是**下一步工作的论点与判据**：论文快路径由三段组成，我们完成了哪两段半、
> 缺的那一段到底是什么、先补哪一段才划算。

---

## 0. 一页结论

| # | 论点 | 一句话 |
|---|---|---|
| **N1** | 论文快路径 = **三段耦合**；我们是 **2.5 段** | stage1 managed launch ✅、stage2 cave/handler ✅、stage3 是 **0317 带外触发**，不是论文的带内触发 |
| **N2** | 0317 能进 handler、cave 可用、**reason 可区分** | 签名 `0x5aa5/0x1`；0317=0x1、launch=0x8；handler 能读自己的 `kernel_idx/killable` |
| **N3** | 真正的缺口是 **host→trap 的 target/request 通道** | 不是一个字段：pbuf 全 0、host/设备写不进、store 不共享；target 与入口/调试 agent 绑定 |
| **N4** | target 提升**选择性**，不直接降**延迟** | 0317 设备停 0.2 ms，但 `Suspend` 返回 22.9–30 ms；reason-armed EXIT 27.4 ms；32 µs 必须回到带内触发 |

**优先级一句话**：

> **先争"入口/延迟"（P1 开闸 / P3 第二入口），再谈"target/选择性"；不要把 target 当成降延迟的捷径。**

## 1. 定义与范围

### 1.1 论文快路径的三段

| 段 | 论文 | 作用 |
|---|---|---|
| **stage1 managed launch** | shim/guardian + debugger params/entry | 让 kernel 可被识别、可被恢复/重放 |
| **stage2 instrumented handler** | 扩展 trap handler | 在 trap 里判据/abort/记录 |
| **stage3 in-band trigger** | ioctl 写 GPU 控制寄存器（`0x419e84`） | 让运行中的 kernel 立即 stall，trap 进正常上下文 |

### 1.2 两个目标，不要混

| 目标 | 含义 | 现状 |
|---|---|---|
| **paper-exact** | 三段完全一致、32 µs、per-queue、handler 内 abort | ❌ stage3 被 `pGpu+0x911` 关 |
| **best-effort** | 用 0317/GDB 达到"停住/让渡/重放/正确" | ✅ 已可用（27 ms / 116 ms） |

### 1.3 范围

- 精确断言：RTX 5060 / 595.99.02、RTX 5090 / 595.71.05（handler 布局一致）；
- A/B：RTX 3090 / 570（229 µs）、A100 / 550（regops 开、handler 缺）；
- 本文的"我们"= stage1/2 的 XSched HAL + cave + 0317 agent。

## 2. N1：论文快路径是三段耦合，我们是"2.5 段"

> **N1 论点**：论文快路径由三段组成；我们已完成 stage1、stage2，stage3 是 0317（带外），
> 不是论文的带内触发。因此当前是 **best-effort**，不是 paper-exact。

### 2.1 证据

| 段 | 我们的证据 | 结论 |
|---|---|---|
| stage1 | `CudaQueueLv3Trap`/`InstrumentContext`：managed launch、debugger params、guardian entry；`run_l3qspin.sh` 可停/重放 | ✅ |
| stage2 | live handler `base+0x15f0f00` 指纹；`+0x390` 注入 8 槽 cave；签名 `0x5aa5/0x1`；5090 fingerprint MATCH | ✅ |
| stage3 | 0317 是 RM 调试器 suspend；`0x419e84` 被 `pGpu+0x911` 关；`cuXtraTriggerTrap` 无副作用 | ⚠️ 只有带外 |

**对照**：

- 3090/sm86/570：三段齐全 → 229 µs、`bad=0`；
- sm120/595：stage1+2 有，stage3 只有 0317 → 27 ms / 116 ms；
- A100/sm80/550：stage3 的 regops 开，但 stage2（sm80 handler）没有 → 内核照跑。

### 2.2 为什么叫"2.5 段"

- stage1+2 是"可被 trap 的 kernel + 可执行的 cave"；
- 0.5 是"0317 能触发 trap，但它是**带外、context 级**，不是论文的带内、per-queue"；
- 所以不能把"0317 触发 + cave"说成"论文快路径复现"。

### 2.3 边界与含义

- **不**声称复现论文；**不**把 27 ms/116 ms 与 32 µs 混为一谈；
- 含义：paper-exact 必须先解决 stage3；best-effort 可以继续做，但天花板受 RM/驱动约束。

### 2.4 可证伪

- 如果 0317 + cave 能达到与论文相同的端到端延迟/语义（无带内触发）→ N1 需要修正；
- 如果找到第二条用户态带内入口 → stage3 补齐。

## 3. N2：0317 能进 handler、cave 可用、reason 可区分

> **N2 论点**：0317 能触发活体 handler；我们能在 `+0x390` 注入 cave；当前配置能区分
> 0317（0x1）与 launch（0x8）；handler 能读自己的 `kernel_idx/killable`。
> 但这是"事件可分"，不是"目标可选"。

### 3.1 证据

| 项 | 观测 | 证据 |
|---|---|---|
| handler 执行 | 签名 `0x5aa5`、`reason=0x1` | `exp_sig_rm0317.log`、`l3x` |
| cave 可用 | `+0x390` patch 回读一致；8 槽；R1 保留 | `run_l3qspin`、`run_l3trap` |
| reason 区分 | 0317=0x1；launch=0x8 | `exp_arm_sentinel_{host,dev}.log` |
| 自己的 idx | `c[0x180]=1`、`c[0x188]=1` | `exp_dbgparam_{180,188}.log` |
| 5090 | fingerprint MATCH；0317 签名 | `evidence/rtx5090_595_71/` |

### 3.2 0317 的四态（详细见 `report/04` §2.2.1/§2.2.2）

- 普通 context → benign trap（内核继续）；
- 受管+InstrMemAllocator → cancel（27–30 ms）；
- NO_ICTX → no-op；
- 预 attach/tracer → park（stop-only；0318 阻塞）。

### 3.3 边界

- **0x1 是通用 SR 位**，不是 XSched 专用标识；换成 0x8 也不保证跨配置；
- 当前 0317 路径建议按**精确值** `R2==0x1`（或 `(R2&0x9)==0x1`），并在目标配置复验 launch；
  如果将来开闸、cmd=2 出现 `0x30`，要按 pbuf 规则扩展门控，不能只用 bit0；
- pbuf 全 0；没有 per-suspend target；
- cave 是 payload，不是"停 context"的机制。

### 3.4 含义与可证伪

- 含义：我们有"这是不是 0317"的判据，没有"该杀谁"的判据；
- 可证伪：若发现 0317 带 XSched 专用 reason，或 pbuf 里有 idx → N2 的目标缺口不成立。

## 4. N3：target/request 是 host→trap 的通道缺口，不是一个字段

> **N3 论点**：target 不是"再读一个偏移"；自然字段是驱动 pbuf `+8`，
> 但 0317 路径驱动不写、host 写不进、launch-time 常量只有自己的 idx。
> 缺的是**通道**，不是字段。

### 4.1 证据：通道矩阵

| 通道 | 读 | 写 | 结论 |
|---|---|---|---|
| 普通全局内存 / CUDA 分配 | **0** | ✅ | 读通路不通 |
| host-mapped UVA | **0** | ✅ | 同上 |
| XSched `c[0x170]` buffer | **0** | host 运行期不可写 | 不是通道 |
| 驱动 pbuf（`.CONSTANT`） | 0317 可读、全 0 | trap ST 不共享；host/设备写失败 | 不是通道 |
| scratchpad | 活动 per-warp 窗口 | 驱动布局内 | 不是通用 mailbox |
| 代码页 / 描述符 LDG | **700** | 需 instr mem API | 不是通道 |
| 常量库 `c[0x170..0x188]` | ✅ | launch-time 固定 | 只有自己的 meta |
| SR | ✅ | — | 只有 reason |

### 4.2 为什么"不是一个字段"

- 论文的 target 不是 host 写的 ID：它是**queue 触发范围 + `kernel_idx`/`preempt_idx` 记账**；
- sm120 的 0317 路径：pbuf `+8` 全 0；host/设备都写不进；`c[0x180]` 只是"我是谁"；
- 所以"补 target"= 补一条 **host 可写、trap 可读** 的通道；这不是 cave 能解决的。

### 4.3 三条可行路径

| 路径 | 谁写 | 前提 | 现状 |
|---|---|---|---|
| 开闸（P1） | 驱动写 pbuf cmd/idx | 专用机 + 驱动/注册表 | 未验证 |
| 调试 agent（P4c） | `IPreemptionBufferAccessor` | libcudadebugger 逆向 | 未实现 |
| 新通道（P3） | 待找 | 未 gate 的入口 | 未找到 |

### 4.4 含义与可证伪

- 含义：target 是**平台/驱动/调试 agent 级项目**，不是一次实验；
- 单 kernel context 里 `kernel_idx` 已隐含 target；多 kernel 才必须通道；
- 可证伪：任一 host 可写、trap 可读的通道出现 → N3 的"缺通道"不成立。

## 5. N4：target 提升选择性，不直接降延迟

> **N4 论点**：target 能让 handler 只杀目标（多 kernel 时有用）；
> 但 0317 是 context 级、27 ms 是驱动 teardown；target 不改变这个下限；
> 要 32 µs 必须回到带内触发。

### 5.1 证据：延迟结构

| 指标 | 数值 | 含义 |
|---|---|---|
| 0317 设备停 | **0.204 ms** | 硬件/驱动停住很快 |
| 0317 `Suspend` 返回 | **22.9–30 ms** | 驱动 cancel/teardown + stream 同步 |
| reason-armed EXIT | **27.4 ms** | handler 内 EXIT 也没降 |
| standalone kill | **0.234 s** | 重放成功，但不是 µs |
| GDB | **116 ms** | CILP 保存 |
| 论文 | **32 µs** | 带内触发 + handler abort |

### 5.2 选择性与延迟要分开

| 目标 | 需要什么 | 现有 |
|---|---|---|
| **选择性**（只杀目标 kernel） | target/request 通道（N3） | 单 kernel：`kernel_idx` 够；多 kernel：缺 |
| **低延迟**（µs） | 带内触发（N1 stage3） | 缺（`0x911`） |

- target 让"杀谁"更准，但不让"停"更快；
- 0317 的 27 ms 是 context 级收尾；即使 handler 只 EXIT 目标，驱动仍要走 cancel/teardown；
- 因此"target id → 32 µs"是把两件事绑在一起，逻辑不成立。

### 5.3 含义与可证伪

- 含义：**先 P1/P3 争延迟，target 作为选择性增强**；不要把 target 当降延迟的捷径；
- 可证伪：若 target+cave 在无带内触发下把 `Suspend` 降到 µs 级 → N4 需要修正。

## 7. 下一步路线（P1–P6）

| 路径 | 目标 | 第一个实验 | 成功判据 | 难度/前提 |
|---|---|---|---|---|
| **P1 开闸** | paper-exact 入口 | 静态找 `0x911` 能力位来源；专用机置 1、重载 | PTIMER 非 0；`0x419e84` 触发；pbuf 可读 | 高；裸金属/root |
| **P3 第二入口** | 绕 gate | 枚举 RPC 变体/escape，做副作用判据 | 任一入口停住内核 | 中 |
| **P4c 调试 agent** | 纯用户态完整路径 | `libcudadebugger`/`DebugAgentMain`/`IPreemptionBufferAccessor` | 无 cuda-gdb 写 pbuf/CILP | 高（月级） |
| **P5 kill+replay** | 可用的 L3 语义 | 0317 + guardian/EXIT + XQueue 重放；单/多 kernel | 结果正确、延迟可接受 | 中 |
| **P6 换平台** | 论文级结果 | 3090/570；GV100；H100 regops | 229 µs / 32 µs | 低（租机器） |
| P6b 控制 | 分离驱动 vs 架构 | 3090 + 595（若支持） | `0x911` 开/关 | 中（装驱动） |

**优先级**：

1. **P1 静态 + P3 枚举**（零成本，先缩小范围）；
2. **P6b 3090+595**（关键控制：驱动 vs 架构）；
3. **P1 裸金属开闸**（唯一判决性实验）；
4. **P4c**（长期、唯一纯用户态）；
5. **P5**（并行，保底可用）。

## 8. 三个近期实验（可直接做）

### E1 单 kernel 的"选择性命中"

- 单 kernel managed context；cave 用 `kernel_idx` 判据只对"我是目标"执行 guard/EXIT；
- 对比 native cancel 的延迟/重放/正确性；
- 目的：验证"target 判据"在单 kernel 下的价值上限（不需要新通道）。

### E2 多 kernel 的 target 缺口

- 同一 context 两个 kernel，尝试只杀一个；
- 预期：没有 target 通道做不到；
- 目的：为 P1/P4c 提供动机与证据。

### E3 reason-armed EXIT vs native cancel

- 27.4 ms vs 27 ms；
- 目的：确认"handler 判据不是延迟瓶颈"，把矛头指向触发路径。

### E4（可选）3090 + 595

- 若 595 支持 sm86，跑 `regops` 看 `0x911`；
- 目的：区分"595 驱动"与"Blackwell 架构"。
