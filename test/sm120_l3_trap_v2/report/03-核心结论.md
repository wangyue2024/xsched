# 03 核心结论：595/Blackwell 关闭了用户态可达的调试寄存器通路，论文的 queue-based 带内 L3 在当前 sm120 配置下不可实现

> 日期：2026-10-27　事实基线：`FINDINGS_ZH.md` §1–§54（2026-10-27）、`report/02-中断入口.md`
> 平台：RTX 5060（sm_120 / 595.99.02）、RTX 5090（sm_120 / 595.71.05）
> 对照：RTX 3090（sm86 / 570.124.04）、A100（sm80 / 550.107.02）

---

## 0. 结论（精确版）

**在 sm120 + 595 驱动、普通用户态、不修改驱动的条件下，XSched 论文（OSDI'25）
queue-based Lv3 所依赖的"带内写 GPU 控制寄存器触发 trap"不可实现。**

原因不是 handler 不会执行，也不是代码写错，而是：

1. 论文的触发要写 `0x419e84`（bit31）；
2. 用户态唯一可达的写入口是 RM `0x20800122`（`EXEC_REG_OPS`）；
3. 内核 handler 在执行这批寄存器操作**之前**检查 `pGpu+0x911`；
4. 该标志在 595/Blackwell 上**启动时被置 0**，且没有运行期 setter；
5. 于是无论寄存器地址是 `0x419e84` 还是别的，操作都不会执行。

**这不是"新架构普遍关闭了用户态访问内核的能力"**，而是：

> **595 这一代驱动对 Blackwell（sm_120）在启动期关闭了"调试寄存器访问"这一项策略能力；
> 同一代/更老的 Ampere + 570/550 是开着的。**

**这也不是"论文方法在任何地方都不可能"**：

- 同一套上游 XSched 代码在 **3090/sm86/570** 上 `level 3` p50 **230–241 µs**、
  200 次抢占后 16M 元素 `bad=0`；
- 所以结论是"**该方法在 sm120/595 的当前配置下不可实现**"，不是"方法本身错"。

---

## 1. 为什么这是 sm120 的"第一根因"

在 sm120 的四道锁里，这一条是**锁①**，而且它决定了后面几道锁的形态：

```
① 触发锁：0x419e84 / cuXtraTriggerTrap → pGpu+0x911 = 0（本文）
   ↓ 打不开
② 请求/判据锁：只能用 0317 的通用 reason（0x1），没有 XSched 专用 reason
③ 输入/目标锁：debugger-suspend 上下文里 pbuf 全 0、没有 target
④ 恢复锁：0318 阻塞、裸 EXIT 破坏重放，恢复归 libcudadebugger
```

如果锁①打开，trap 会走**正常内核上下文**（像 sm86），第②③④道锁的现象**可能一起消失**
——这是推断，但也是"改一个开关可能解开四道锁"的唯一支点。因此它既是第一根因，
也是最值得和导师讨论的决策点。

## 2. 论文依赖的触发机制（外部锚点）

OSDI'25 §6.3（p.679）原文：

> "we discovered a specific **ioctl** that triggers GPU interrupts by **writing to a GPU
> control register** … it immediately **stalls all running kernels** and invokes the
> **trap handler to save context and check trap reason** … XSched extends the trap handler
> to **detect interrupts triggered by XSched** … the **target kernel is aborted**."

上游代码里的对应关系：

| 环节 | 代码/常量 |
|---|---|
| 触发调用 | `platforms/cuda/hal/src/level3/interrupt.cpp:105` → `cuXtraTriggerTrap(kCtx)` |
| 接口 | `3rdparty/cuxtra/include/cuxtra/cuxtra.h:152` |
| 寄存器 | `0x419e84` bit31（sm86/570 A/B 实测有效） |
| 经手命令 | RM `0x20800122`（`NV2080_CTRL_CMD_GPU_EXEC_REG_OPS`） |

**所以：论文的模型依赖"用户态能写这个控制寄存器"这一前提。** 本文只论证这个前提在
sm120/595 上不成立。

## 3. 证据链（从接口到副作用）

### 3.1 接口是什么

`0x20800122` 不是函数，是 RM 命令号；用户态通过：

```
ioctl(fd, NV_ESC_RM_CONTROL = 0xc020462a,
      &NVOS54{ hClient, hObject = subdevice, cmd = 0x20800122,
               params = &blob(48B), paramsSize = 0x30, status })
```

内核分发：`subdeviceCtrlCmdGpuExecRegOps_IMPL@0x2dd410`
→ `subdeviceCtrlCmdGpuExecRegOps_cmn@0x2dcfc0`。
参数块含 `regOpCount` 与 `regOps[]`（32 B stride，读/写、寄存器 offset、value、mask）。
**它是通用的"批量读写 GPU 寄存器"入口**，`cuXtraTriggerTrap` 最终经它写 `0x419e84`。

**`0x419e84` 不在内核驱动里**：按字节扫描，nv-kernel 0 处，`libcuda.so.595.*` 多处
（595.99 反汇编 13 处）、`libcuxtra.a` 2 处 ⇒ 寄存器地址由用户态描述符传入，
内核只负责"执行这批 op"。

### 3.2 闸门是什么

`pGpu` 是内核 OBJGPU 对象的指针，`+0x911` 是该对象里的一个 `bool` 字段
（**不是硬件寄存器**，用户态不可见）。初始化代码：

```
0x17354  mov $0x2, %esi
0x17359  shr %cl, %rsi          ; 对某个 64 位能力/配置值做位测试
0x1735c  test %rsi, %rsi
0x1735f  je   ...
0x17376  movb $0x1, 0x911(%rdi) ; 满足 -> 置 1
0x17b4c  movb $0x0, 0x911(%rdi) ; 另一分支 -> 置 0
```

- **全二进制只有这两处写 `0x911`**，都在 `__nvoc_init_dataField_OBJGPU`；
- **没有运行期 setter**；
- 读点很多（20+，多个调试/reg-op 路径共用），说明它是一个"全局 debug/reg access 允许"标志。

### 3.3 gate=0 时会发生什么（静态）

| 路径 | 反汇编 | 结果 |
|---|---|---|
| subdevice `0x20800122` | `0x2dd120 xor eax,eax; 0x2dd122 cmpb $0,0x911(%r12); je 0x2dd02a` | **返回 NV_OK，跳过寄存器写** |
| 会话 `0x83de031d` | `0x21a9cc cmpb $0,0x911(%rbx)`；为 0 时 `mov $0x56,%eax; ret` | **返回 0x56，不进入执行分支** |

### 3.4 动态验证：两个 sm120 平台一致

**RTX 5060 / 595.99.02**

| 测试 | 结果 |
|---|---|
| `regops` 读 `PMC_BOOT_0`（`0x0`，应为非零芯片 ID） | **0**，status `0x3a` |
| 读 `PTIMER_TIME_0/1`（应为非零且递增） | **0 / 0**，status `0x3a` |
| `read w/ channel`（控制返回成功的变体） | **status=0，value=0** |
| 写 `0x419e84` bit31 | **status=0x3a**，无副作用 |
| `cuXtraTriggerTrap` | 立即返回，内核计数 36.9 M/s 继续，不冻结 |

**RTX 5090 / 595.71.05**（同 sm_120，不同驱动 build）

| 测试 | 结果 |
|---|---|
| 读 `PMC_BOOT_0` / `PTIMER` | **0 / 0 / 0**，status `0x3a` |
| `read w/ channel` | **status=0，value=0** |
| 写 `0x419e84` bit31 | **status=0x3a**，无副作用 |

**关键对照**：如果只是 `0x419e84` 这个地址不对，那么读 PTIMER/PMC（不同地址）应该正常；
它们也读 0 ⇒ **坏的是整条 reg-op 通路，不是地址**。`status=0` 但 `value=0` 正是
"控制成功、op 被跳过"的签名（gate 早退）。

### 3.5 对照平台：同一套代码是能跑的

| 平台 | 驱动 | reg-op 锁 | 结果 |
|---|---|---|---|
| RTX 3090（sm86） | 570.124.04 | **开** | `level 3` p50 **230–241 µs**、p99 0.42–2.8 ms、restore 93–127 µs；200 次抢占后 `bad=0` |
| A100（sm80） | 550.107.02 | **开**（能读 `0x200510/0x419e84`，写 bit31 返回 0） | 但 sm80 不在上游 TarpHandler 支持列表，handler 未插桩 → 内核照跑；带 shim 还崩在 `cuXtraKernelGetFunction` |
| RTX 5060（sm120） | 595.99.02 | **关** | 0317 27 ms / GDB 116 ms |
| RTX 5090（sm120） | 595.71.05 | **关** | 0317 / GDB 可用；带内触发不可用 |

⇒ **不是 "Blackwell 架构不支持 trap"**：3090 证明方法可行；A100 证明锁可以开；
5060/5090 证明 595/Blackwell 这一组合关掉了它。

### 3.6 也不是 handler 的问题

| 事实 | 证据 |
|---|---|
| 活体 handler 可定位、可注入、可执行 | 签名 `0x5aa5/reason=0x1`；`run_l3trap`/`l3x` |
| sm120 handler 布局与 595.99 一致（5090 实测） | slot20 `0x880/0x940`、tools image `base+0x15f5300`、`.text.do_pause` **0/160 mismatch**、live `base+0x15f0f00` **fingerprint MATCH** |
| 0317 在 5090 上也能进 handler | `l3x` target/agent → `0x5aa5/0 reason=0x1` |
| GDB 冻结/恢复可用 | 5060 GDB backend 116 ms；5090 attach 3 s hold 冻结（wall +3.12 s） |

**所以失败点是"入口不让你写寄存器"，不是"handler 坏了"。**

## 4. 证据强度：哪些是确凿的，哪些还不是

| 结论 | 强度 | 依据 |
|---|---|---|
| **E1** 5060/595.99 与 5090/595.71 上，`0x20800122` 被 `pGpu+0x911` 在写前拦截 | **确凿** | 反汇编 + 两机动态 + `status=0/value=0` |
| **E2** `0x419e84` 由用户态描述符传入，不在 nv-kernel | **确凿** | 字节扫描（nv-kernel 0、libcuda/cuxtra 多处） |
| **E3** gate=0 时所有寄存器（含 PTIMER/PMC）都不执行 | **确凿** | 反汇编返回路径 + 读 0 + 计数不停 |
| **E4** 3090/570 上同一接口可用、论文方法可复现 | **确凿** | 3090 A/B 229 µs + `bad=0` |
| **E5** 因此"当前 sm120/595 + 普通用户态 + 不改驱动"下，论文的带内触发不可实现 | **条件确凿** | E1–E4 直接推出；条件是"当前驱动/不改/用户态" |
| **E6** 没有任何其他用户态可达的触发入口 | **未证（经验性）** | 已枚举 RM controls、cuxtra、0317、tracer、BAR0；RPC 变体未全验 |
| **E7** 595 装到 Ampere 也会关 / 只与架构有关 | **未证** | 没有 595-on-Ampere 交叉；不能把原因唯一归给架构 |
| **E8** 打开 `0x911` 后论文语义会恢复 | **推断** | 正常上下文 → 全局读/pbuf/状态机可能恢复；需专用机反事实 |
| **E9** `0x911` 的能力位来自哪个注册表/模块参数 | **未知** | `0x17354` 的位测试是入口，具体键未定位 |

**一句话**：**"锁被关了"是确凿的；"关它的最终原因/能不能合法打开/有没有别的入口"还没有闭环。**
汇报时不要把 E6–E9 说成已证。

## 5. 反方观点与回应

| 反方 | 回应 |
|---|---|
| "是不是 `0x419e84` 这个地址在 Blackwell 上变了？" | 不是首选解释：地址在 550/570/595 的 libcuda 里都是硬编码（595 反汇编 13 处）；且 gate 在写之前，换地址也轮不到执行。地址是否是 Blackwell 专用仍是未证项，但不是当前主因。 |
| "是不是你们没找对 ioctl/命令？" | 接口、命令号、参数块、内核 handler 都已定位；`0x20800122` 有返回码、动态可调；问题是 gate，不是找不到。 |
| "是不是 handler 没执行/注入失败？" | 签名、指纹、0317、GDB 全部通过（§3.6）。 |
| "是不是 5060 这块卡的问题？" | 5090/595.71 同样关闭（§3.4）。 |
| "是不是所有新架构都这样？" | 不能这么说。3090/570、A100/550 是开的；只能说到 595/Blackwell 这一组合。缺 595-on-Ampere 交叉。 |
| "那论文是不是错的？" | 不是。同一套代码在 3090/570 上 229 µs、结果 bit-correct；错的是"这套入口在 sm120/595 上可用"这个前提。 |
| "那 sm120 就不能做 L3 了？" | 能做**替代形态**：GDB freeze（116 ms）、0317 debugger-suspend（27 ms）、park-only；但不是论文的 32 µs 带内路径。 |

## 6. 可证伪条件（任一成立即修正本文）

1. 在 5060/5090 上找到**运行期**写 `0x911` 的路径（模块参数/注册表/驱动 patch），
   写 `0x419e84` 后出现与 0317 不同的 reason → "入口被关"不成立（或不是唯一入口）。
2. 任一用户态可达的 RM control/escape 在不建调试器会话的前提下让运行中内核停住
   → "只有 0317/GDB"不成立。
3. 595 装到 Ampere 后 `0x911` 仍为 0 → 说明是驱动版本策略，不是架构；
   若为 1 → 说明是架构/组合策略（本文的"595/Blackwell"表述要改）。
4. 同一台 sm120 打开 gate 后，论文 payload 仍然读不到 preempt buffer / 不能重放
   → "开闸能一并解开四道锁"的推断不成立。

## 7. 结论的边界与替代路径

**本文结论的准确边界**：

> **不是**"新架构普遍关闭了用户态访问内核的能力"；
> **不是**"论文方法在任何平台都不可能"；
> **是**"595/Blackwell 在启动期关闭了用户态可达的调试寄存器通路，
> 因此论文的 queue-based 带内 L3 在当前 sm120/595、普通用户态、不改驱动的条件下不可实现"。

**替代路径**（都不是论文原机制）：

| 路径 | 现状 | 代价 |
|---|---|---|
| GDB backend（冻结/恢复） | 可用 | 116 ms 设备静止；需 cuda-gdb |
| RM 0317 debugger-suspend | 可用 | 27–30 ms；需会话/应答；不能原地恢复 |
| park-only | 可用 | 停住不释放 |
| 打开 `0x911`（驱动/注册表/专用机） | 未验证 | 需 root + 重载驱动；可能同时恢复论文语义 |
| 进程内调试 agent | 未实现 | 唯一纯用户态完整路径；工作量大 |
| 换平台（3090/570、GV100） | 已验证/论文原平台 | 直接拿到 229 µs / 32 µs |

## 8. 汇报口径（一页 slide + 一句话）

**一句话**：

> "论文 L3 依赖的带内寄存器触发，在 595/Blackwell 上被驱动**启动期策略性禁用**
> （`pGpu+0x911`），用户态无法通过 `0x20800122` 写 `0x419e84`；这不是 handler 或
> 我们代码的问题——同一套 XSched 在 3090/570 上 229 µs、结果 bit-correct。
> 因此 **sm120 的论文级 L3 在当前驱动下不可达**，除非驱动配合开闸、换平台，
> 或走调试 agent 的替代路径。"

**一页 slide 建议**：

| 项 | 内容 |
|---|---|
| 结论 | 595/Blackwell 关闭 reg-op；论文带内 L3 在当前配置不可实现 |
| 证据 1 | `0x911` 只在 init 写两次；reg-op handler 在写前检查（反汇编） |
| 证据 2 | 5060/5090：PTIMER/PMC 读 0、写 `0x419e84` status 0x3a（两机一致） |
| 证据 3 | 3090/570：同一接口 229 µs、`bad=0`（方法可行） |
| 证据 4 | handler 可注入/0317/GDB 均可（不是 handler 问题） |
| 边界 | 不是"所有新架构"、不是"永远不可能"；需驱动配合/换平台 |
