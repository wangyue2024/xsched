## Q1 总结目前的进度

**结论**：sm120 上已有可用的 L3（GDB backend）和可复现的 trap 原语；trap-native
的"停住且原地恢复"仍不可达。

### 已达成

1. **生产可用 L3（GDB backend）**
   - `GdbInterruptContext` + `l3ctl` + `xcli l3`；
   - 设备静止 **116 ms**、预热后 attach ~23 ms、handover 0.73–0.74 s、`Resume=1`；
   - suspend→resume 结果 bit-exact。

2. **trap 原语**
   - 活体 `.text.traphandler` 定位（`base+0x15f0f00`，10 条指纹）；
   - `+0x390` 注入 `CALL.ABS` 到 cave，或 `+0x880` 装上游 payload；
   - 注入代码确定执行（签名 `0x5aa5`）；
   - standalone kill：8 s 内核 → **0.234 s**、`cudaSuccess`。

3. **受管上下文**
   - managed launch 走 shim 的 `cuLaunchKernel` → `CudaKernelLaunchCommand`；
   - `0317` 在 **27–30 ms** 内让计数冻结、stream 判完成；
   - 设备真正冻结只要 **0.204 ms**（会话预建），22.9 ms 是驱动 teardown；
   - kill + 队列重放已闭环；裸 `EXIT` 会破坏重放（v6.8）。

4. **park**
   - CUDA init 前进程已在外部 tracer 下（`strace -f` 或 plain gdb，不需要 cuda-gdb）；
   - 再加 `0317` → 真 park（计数冻结、`Synchronize` 不返回）；
   - 但无用户态释放手段（`0318` 全 client 阻塞）。

5. **判据推进（v6.5–v6.8）**
   - handler 能读 `c[0x170]` preempt_buf、`c[0x178]` guardian、
     `c[0x180]` kernel_idx、`c[0x188]` killable；
   - 当前配置 `0317=0x1`、`launch=0x8`，事件可区分；
   - 驱动 pbuf 在 0317 陷阱里可读但全 0；trap 内 store 不 fault 但不共享；
   - 仍缺 per-suspend 的 **target ID** 与 **request** 的 host→trap 通道。

6. **A/B**
   - 上游 `XpuOS/xsched` 在 RTX 3090（sm86/570）跑通论文 L3：
     p50 **230–241 µs**、restore 93–127 µs、200 次 suspend/resume 后 `bad=0`；
   - 去 shim 退化到 6–40 ms；
   - A100（sm80/550）cuxtra 崩；sm120 触发被 `pGpu+0x911` 关闭。

### 未达成

- trap-native 的"停住且原地恢复"；
- 不依赖调试器的恢复；
- per-kernel 选择性抢占（target ID）；
- 论文级 32 µs（sm120 的用户态入口不存在）。

## Q2 sm120 相比之前架构最大的不同？为什么做不到论文效果？

### 最大不同：中断入口的所有权

论文 L3 的前提是：**用户态能用一条带内 ioctl 写 GPU 控制寄存器，让 GPU 立刻 stall
所有 kernel 并进 trap handler**，XSched 靠 **trap reason** 识别"这是我要的抢占"。

| 维度 | Volta / Ampere（GV100 / sm70 / sm86） | Blackwell sm120 + 595 |
|---|---|---|
| 触发 | `0x20800122`（regops）开放 → 写 `0x419e84` bit31 → 带内中断 | `0x20800122` 被启动期 `pGpu+0x911` 早退，写 `0x419e84` 无效果 |
| CUDA API | `cuXtraTriggerTrap` 生效 | 同一调用无法投递 |
| 可用中断 | 带内、由触发者编码 | 只剩 RM `0x83de0317` debugger-suspend |
| 语义 | 调度原语（XSched 所有） | 调试器状态机（GSP + libcudadebugger 所有） |
| reason | 可区分来源 | 旧：恒 0x1；v6.8：0x1 vs launch 0x8，但仍无 target |
| 请求载体 | XSched 自己的 preempt buffer（host 可写） | 驱动私有 pbuf（用户态不可写） |
| 恢复 | host 重跑幂等 kernel | `0318` 全 client 阻塞，只有调试 agent 能释放 |

### 为什么做不到论文效果：四道锁

1. **触发锁**：`pGpu+0x911` 是启动期能力位，运行期无写点；
   `0x20800122` / `0x83de031d` 在闸门处 `return NV_OK`，静默 no-op。
2. **请求/判据锁**：0317 的 reason 历史上恒 0x1；v6.8 当前配置虽能区分
   0317(0x1) 与 launch(0x8)，但没有 per-suspend target ID，且 0x8 不保证跨配置。
3. **输入/目标锁**：handler 能读 launch 固定参数，但读不到 pbuf 数据；
   host 无法写 pbuf（cuXtra 运行期 invalid、设备 store 非法、CPU 零页），
   因此无法告诉 handler "这次杀谁"。
4. **恢复锁**：`0318` 在所有 client 阻塞；`0317` 是通道级挂起 + 队列重放，
   不是 CILP 原地恢复；裸 EXIT 会破坏驱动 trap 状态机。

**结论**：不是 handler 不行，而是**叫醒 handler 的方式和它能拿到的信息都变了**。
27 ms/116 ms 是结果；根因是入口 + 判据 + 恢复归属。

## Q3 带内 ioctl 触发在 sm120 上是"不存在"还是"没找到"？

**结论：接口存在、入口已定位，是被软件闸门关死；"硬件不支持"尚未证明；
GSP 固件层尚未穷尽。**

### 1. 驱动接口层：存在

论文那条路在 595 驱动里的对应物已定位到函数级，共两条 RM 通路：

| 通路 | 函数 | sm120 行为 |
|---|---|---|
| `0x83de031d` DebugExecRegOps（调试会话级） | `ksmdbgssnCtrlCmdDebugExecRegOps_IMPL@0x21a990` | `if (!*(NvBool*)(pGpu+0x911)) return NV_OK;` |
| `0x20800122` GPU_EXEC_REG_OPS（subdevice 级，不需要调试器会话） | `subdeviceCtrlCmdGpuExecRegOps_cmn@0x2dcfc0` | 同样 `cmpb $0x0,0x911(%r12); je → return NV_OK` |

两条都能走完参数解析、抵达闸门前，然后**静默早退**（返回成功但零副作用）。

### 2. 闸门：`pGpu+0x911` 启动期写入

全 `.text` 扫描 `nv-kernel.o_binary`，写 `0x911` 的指令**只有两处**，都在
`__nvoc_init_dataField_OBJGPU`（GPU attach / 驱动加载时执行一次），
值由初始化时读到的能力位/注册表位决定：

```
0x17359  shr %cl,%rsi          ; 测试能力/注册表位
0x1735f  je  0x17082           ; 不满足 -> 不置位
0x17376  movb $0x1,0x911(%rdi) ; 只有这条路径会打开
0x17b4c  movb $0x0,0x911(%rdi) ; 否则置 0（本机走这条）
```

RM 侧没有控制命令能改它。要打开只能改模块参数/注册表并重载驱动
（`rmmod nvidia`），超出本项目的安全边界。

### 3. 三个"未验证"

| 问题 | 结论 |
|---|---|
| 论文那条 ioctl 在 sm120/595 上可用吗？ | 不可用，已被软件闸门关闭（有函数级证据） |
| sm120 硅片本身支持吗？ | 未证明不支持；间接证据倾向"软件策略"（sm86/570 同机制可用、A100 regops 开放） |
| 是否还有别的带内入口？ | 未穷尽；GSP 固件 RPC 层未做，BAR0 直写属于危险操作未做 |

**注意**："让 GPU stall 并进 trap handler"这个能力在 sm120 上存在（0317/GDB 就是靠它）；
缺的是**用户可编程的带内触发 + 可区分的 reason**。

## Q4 目前的 trap 触发方式和论文的有什么不同？

**一句话**：论文是调度器自己写 GPU 控制寄存器制造带内硬件中断；我们是向驱动建
调试器会话，发 `0x83de0317` 让它"暂停这个 context"。

| 维度 | 论文 / 上游（sm70/sm86） | 我们（sm120/595） |
|---|---|---|
| 触发调用 | `cuXtraTriggerTrap(kCtx)` → regops `0x20800122` → 写 `0x419e84` bit31 | `rm_control(fd, 0x83de0317, {z,0})` |
| 通路 | 带内：硬件立即 stall 所有 kernel | 带外：RM 命令进 GSP/驱动调试状态机 |
| 触发进程 | 调度器/进程内运行时 | 必须是外部 agent client（target 自发是 no-op），需 `0xd04` 授权 |
| 前置条件 | 无会话、无授权、无调试器 | 0x83de 会话 + 0xd04 + 调试器/tracer |
| 粒度 | hwQueue / kernel 级 | CUcontext 级 |
| 谁保存上下文 | XSched 插桩的 handler | 驱动/GSP 的 debugger 状态机做 CILP save |
| 判据 | 可区分 reason | 旧：恒 0x1；v6.8：0x1 vs 0x8，但无 target |
| handler 输入 | XSched 自己的 preempt buffer（host 可写） | 驱动私有 pbuf（用户态不可写）；数据读回 0 |
| abort | handler 内 EXIT 只杀目标 | 默认驱动 cancel；裸 EXIT 破坏重放 |
| 恢复 | host 重跑幂等 kernel | 0318 全 client 阻塞，需调试 agent |
| 延迟 | 32 µs（GV100）/ 229 µs（sm86） | 0.204 ms 停 / 22.9 ms 返回 / 27–30 ms cancel / 116 ms GDB |

**一样的部分**：最终都进入同一个 `.text.traphandler`，都执行我们注入的 SASS。
**不同的部分**：触发者、通路、粒度、判据、输入、恢复所有权。

## Q5 0317 是什么？和直接写 419 有什么区别？都能触发 trap 代码吗？

### 0317 的身份

| 项 | 值 |
|---|---|
| 编号 | `0x83de0317`（method 0x0317，class 0x83de） |
| 名字 | **DebugSuspendContext** |
| 所属 | `KernelSMDebuggerSession`（调试器会话） |
| 参数 | 8 B（实测 `{0,0}` / `{1,0}`，语义未完全确定） |
| 实现 | 转发 GSP；本地无 IMPL |
| 配对 | `0x83de0318` DebugResumeContext（psize 0） |
| 调用 | `rm_control(fd, 0x83de_session, 0x83de0317, args, 8)` |

它是"对一个调试器会话说：挂起这个 context"，和 `0315/0316`（调试读写内存）、
`031d`（ExecRegOps）同属一张表。

### 与直接写 `0x419e84` 的区别

| 维度 | 写 `0x419e84` bit31 | 发 `0x83de0317` |
|---|---|---|
| 本质 | GPU 控制寄存器写（经 regops） | RM 命令，转发 GSP 调试状态机 |
| 层次 | 带内，硬件直接反应 | 带外，软件状态机 |
| 作用域 | 设备级 stall 所有 kernel | 单个 context |
| 前置条件 | regops 权限（sm120 被关） | 0x83de 会话 + 0xd04 + 调试 agent |
| 完成模型 | fire-and-forget | RPC：可能阻塞 / `0xffff` / 27 ms cancel |
| 副作用 | 无状态 | 会话/调试参数改变上下文语义 |

### 都能触发我们的 trap 代码吗？

**都能进同一个 handler，但 0317 是否让注入代码拿到控制权取决于上下文配置：**

| 场景 | 0x419e84 | 0317 |
|---|---|---|
| 普通 CUDA 上下文 + 签名 cave，无 gdb | 能（sm86 论文路） | 能：签名 `0x5aa5`、reason `0x1`、内核继续（`exp_sig_rm0317.log`） |
| 受管 + `NO_INSTR` | — | 能：探针进 handler，reason `0x1` |
| 受管 + `PLAIN_LAUNCH`（有 params、无 guardian、无 instr-mem） | — | 能：reason `0x1`、`c[0x170]` 合法 |
| 受管 + 默认插桩（InstrMemAllocator） | — | **退化为 context 级 cancel**；cave 是否执行取决于配置：默认 payload/未 arm 时常拿不到控制权；`TRAP_CAVE`+arm-at-Trigger+lazy session+ack 下 cave **可执行**（`R2=0x1`，`exp_arm_sentinel_host.log`），但**不能用 cave 阻止 cancel** |
| 预 attach / init 前 tracer | — | 内核 park，但 handler 侧无释放手段 |

准确表述：**0317 确实能进 trap handler（不需要 cuda-gdb），但在 XSched 默认的
插桩受管上下文里，驱动的 context cancel/suspend 是主路径；cave 可以执行、记录、
甚至 EXIT 当前 warp，但不能改变"驱动已经决定 cancel 这个 context"的结局。**
"cave 执行"与"cave 有决策权"是两件事。

### 除此之外的不同

1. **谁保存/恢复现场**：0x419e84 路 XSched 掌控，abort 后 host 重跑；
   0317 路 GSP 先做 CILP save，恢复归 0318/调试 agent。
2. **判据**：0x419e84 带可识别 reason；0317 历史上 reason 恒 0x1，
   v6.8 当前配置可与 launch 0x8 区分，但没有 target。
3. **粒度**：0x419e84 设备级 stall，handler 只 abort 目标；
   0317 是 context 级，不能选 kernel。
4. **可恢复性**：0x419e84 不需要调试器；0317 park 后 0318 全阻塞。
5. **跨进程与生命周期**：0317 必须外部 agent + `0xd04`，且有会话副作用；
   0x419e84 无状态。

## Q6 为什么 0317 有时 cancel、有时 park、有时 no-op？

取决于上下文在创建/运行时的"调试器管理态"：

| 上下文状态 | 0317 结果 | 原因/证据 |
|---|---|---|
| 普通 CUDA（l3x） | benign trap，内核继续 | 没有 debugger params/instr-mem（`exp_sig_rm0317.log`） |
| 受管 + `InstrMemAllocator` | cancel（27–30 ms） | `cuXtraInstrMemBlockAlloc` 把 context 切进 debugger-managed（v4.3/v4.5） |
| 受管 + `NO_ICTX_INSTRMEM` | no-op | 不进入调试状态，0317 不投递 trap（`exp_no_ictx_instrmem.log`） |
| CUDA init 前已有外部 tracer | park | 驱动在 `cuInit`/上下文创建时记录 trace 关系（v5.9 §42） |
| cuda-gdb 的 agent 在场 | cancel | agent 应答 suspend，驱动走 cancel 路径（`exp_gdb_cancel1.log`） |

**关键点**：这不是"0317 参数不同"，而是**上下文状态不同**。同一发 0317 在不同状态下
语义不同，这也是为什么"停住且可恢复"的 RM 组合一直拼不出来。

## Q7 27–30 ms 和 116 ms 分别花在哪？

### trap 路径（0317）

| 阶段 | 时间 | 说明 |
|---|---|---|
| req → 设备真正冻结 | **0.204 ms** | 会话预建、eager；计数立即不动 |
| req → `XQueueSuspend` 返回 | **22.9 ms** | 停住后的驱动异步取消清理 + stream 同步 |
| 受管默认 cancel 整体 | 27–30 ms | 含懒建会话（首次 +4.72 ms）与队列 `StreamSynchronize` |
| 首次触发（懒建会话） | 4.72 / 27.3 ms | 会话创建 + shm 轮询 |
| host arm（cuXtra 写 cave） | ~2.1 s | 被运行中内核串行化 |
| 设备 arm（writer 内核） | 0.2 ms | 但 launch trap 会命中新载荷 |

### GDB 路径

| 阶段 | 时间 | 说明 |
|---|---|---|
| 设备静止（CILP save） | **116 ms** | 驱动/固件保存上下文的物理时间 |
| 真实 attach | ~23 ms | `Prepare` 预热后 |
| `Suspend()` 脚本口径 | 0.52–0.54 s | 含脚本自身 0.5 s sleep |
| gdb 进程启动 | ~0.3 s | 预热可省 |

**结论**：停住本身不慢（0.2 ms 级）；27 ms 是 cancel/teardown，116 ms 是 CILP save。
论文 32 µs 的前提是 handler 内直接 abort，让 stream 立即完成，没有这些收尾。

## Q8 handler 到底能读什么、能写什么？

必须区分 **"地址可读"** 与 **"读到有效数据"**。

### 读（三分类，v6.7 定稿）

| 类别 | 来源 | 结果 | 证据 |
|---|---|---|---|
| 读到有效数据 | `c[0x0][0x170..0x188]`、`SR`（reason）、local stack | 可用 | `exp_dbgparam_*.log` |
| 不 fault 但恒 0 | 自建 `cuMemAlloc`、XSched preempt buffer、host-mapped UVA | 0 | `exp_mem_probe2.log`、`exp_uva_probe1.log` |
| 不 fault 但恒 0（补充） | **0317 陷阱里的驱动 pbuf**（`base−0x8000000`） | +0/+4/+8 全 0 | `exp_arm_pbuf_*.log` |
| fault（700） | 代码页、描述符 `LDG`、launch trap 时的 pbuf（重定位）、scratchpad 盲访 | 不可用 | `exp_code_probe1.log`、`exp_ldg_probe1.log` |

**launch 固定参数（实测）**：

```
c[0x170] = preempt_buf（8 B，指针可读、内容读 0）
c[0x178] = guardian（8 B）
c[0x180] = kernel_idx（8 B，实测 1）
c[0x188] = killable（4 B，实测 1）
```

### 写

| 目标 | 结果 | 证据 |
|---|---|---|
| 用户全局内存 / host 映射 shm | 可写，host 回读一致 | `exp_sig_*`、`exp_shm_*` |
| scratchpad 的 per-warp 记录内 | 可写（驱动布局内） | FINDINGS §44 |
| 驱动 pbuf（launch trap 中） | `ST.E` 即 700 | §39 |
| 驱动 pbuf（0317 trap 中） | store **不 fault**，但不与驱动共享，行为无效 | `exp_arm_pbuf_write_r2.log` |
| host / 设备 kernel 写 pbuf | invalid / SIGSEGV / Illegal Address / COW 零页 | §37–§39 |

**结论**：出方向（trap→host）通；入方向（host→trap）在纯用户态不通。
v6.8 更正：`ST.E 写 pbuf 必 700` 只对 launch trap 成立；0317 陷阱里能 store 但无效。

## Q9 既然 reason 能区分 0x1/0x8，为什么还不能实现论文效果？

**因为"能识别事件"不等于"能选择目标"，更不等于"能安全 abort 并重放"。**

1. **只有事件，没有 target**
   - `R2=0x1` 只能说明"这是 0317"，不能说明"要杀哪个 kernel"；
   - handler 能读自己的 `kernel_idx`，但没有 host 写入的 `target_kernel_idx`；
   - pbuf 数据全 0，host 无法写 pbuf。
2. **跨配置不稳定**
   - v4.3 曾见 launch 带 bit0；v6.8 当前配置 launch=0x8；
   - 生产判据应使用精确值 `R2==0x1`，并在目标配置复验 launch reason。
3. **裸 EXIT 破坏重放**
   - reason-armed EXIT 确实只杀 0317、不误杀 launch；
   - 但随后 `trap reactivate: log=0`，重放没有发生，最终 `cudaErrorIllegalAddress`；
   - 能干净重放的仍是"benign return + 驱动原生 do_pause + 通道挂起"（27 ms）。
4. **粒度仍是 context**
   - 即使拿到 target，0317 的挂起是 context 级；
   - 单 stream、单 kernel 场景够用，多 kernel 选择性尚未验证。

**当前可写出的逻辑**：

```
if (R2 == 0x1 && my_kernel_idx == target_kernel_idx) EXIT;
```

缺的正是 **target_kernel_idx + request 的 host→trap 通道**，以及"EXIT 后如何让队列
安全重放"的驱动协作。

## Q10 还差什么才能做到"只杀目标 kernel + 从头重跑"？

### 缺件清单

| 缺件 | 现状 | 候选通道 |
|---|---|---|
| **request**（这是抢占，不是 launch） | 当前配置可用 reason 精确值区分 | 已具备（0x1 vs 0x8），需跨配置复验 |
| **target ID** | 无 | 无纯用户态通道；pbuf 数据读 0、host 不可写；scratchpad 私有 |
| **选择性 abort** | 机制有（EXIT） | 拿到 target 后可写比较逻辑 |
| **安全重放** | 裸 EXIT 会破坏 trap 状态机 | 需要驱动协作或调试 agent 恢复 CILP/命令字 |
| **多 kernel/多队列验证** | 未做（只测单 stream 单 kernel） | 需构造多 queue 场景 |

### 可行的三条路

1. **进程内调试 agent**（唯一纯用户态完整路径）
   - 复用 `libcudadebugger`：`DebugAgentMain` / `cudbgApi*` / `IPreemptionBufferAccessor`；
   - 由 agent 写 preempt 命令字（`cmd=2/1`）、应答 0317、做 restore；
   - 协议样本：`../evidence/live/gdb_agent_protocol.log`。
2. **打开 `pGpu+0x911`**
   - 改模块参数/注册表并重载驱动，恢复 regops 与带内触发；
   - 属于修改驱动行为，超出当前安全边界，需要明确授权。
3. **换平台**
   - sm86/570 已验证（p50 230–241 µs）；GV100/sm70 是论文原始 32 µs 的平台。

**不建议**：继续在 RM 命令里找 mailbox（0313/0314/0321–0324/0329 等已扫，
0315/0316 只认 RM memobj，pbuf 通道已关闭）。

## Q11 sm120 到底能不能做 L3？现在有哪些可用形态？

**能，但语义分三种，只有一种能原地恢复。**

| 形态 | 能力 | 延迟 | 适用场景 |
|---|---|---|---|
| GDB backend | 停住 + 恢复，结果正确 | 设备静止 116 ms，attach ~23 ms | 生产交付、需要正确恢复 |
| trap kill + 队列重放 | 杀 + 从头重跑 | 27–30 ms（cancel）/ 0.234 s（standalone） | 幂等内核的快速抢占 |
| park-only | 真 park，不丢工作，不可释放 | 0.2 ms 级停住 | 驱逐/销毁/整进程回收 |
| 论文式 handler abort | 不依赖调试器 | 32 µs（GV100）/ 229 µs（sm86） | **sm120 不可用**（触发被关） |

**严格结论**：sm120 上"能停能恢复"的形态是 GDB backend；
"trap-native + 可恢复"在纯用户态不可达，缺的是带内触发与 target/request 通道。

## Q12 为什么论文 32 µs、sm86 229 µs、sm120 27 ms？

三者机制不同，不是同一路径的优化差异：

| 平台/路径 | 数字 | 机制 |
|---|---|---|
| GV100（sm70）论文 | **32 µs** | 带内 ioctl 触发 + 插桩 handler 内 abort + 从头重跑；stream 立即完成 |
| RTX 3090（sm86/570） | **230–241 µs** | 同一机制：managed launch + `TarpHandlerSM86` 插桩 + `cuXtraTriggerTrap` |
| sm120（595）trap | 0.204 ms 停 / 22.9 ms 返回 / 27–30 ms cancel | 触发被关，退到 0317 调试器 suspend；驱动 cancel/teardown |
| sm120（595）GDB | 116 ms | 调试器 attach，CILP save 的物理时间 |

论文 32 µs 是 GV100 的数字；sm86 的 229 µs 仍是同一机制，量级可接受；
sm120 的 27 ms 是"借调试器通道"的成本，不是 handler 本身慢。

## 附：事实 / 推断 / 未验证清单

### 已验证事实（有日志/代码）

- `0x20800122` / `0x83de031d` 在 `pGpu+0x911==0` 时静默返回 `NV_OK`；
- `0x911` 全二进制只有两处写，均在 `__nvoc_init_dataField_OBJGPU`；
- `0317` 能进普通/无 instr-mem 上下文的 trap handler（签名/reason 可证）；
- 受管默认上下文的 `0317` 是 cancel（27–30 ms）；
- 外部 tracer 预置 + `0317` → park；
- `0318` 在所有 client 阻塞；
- handler 能读 `c[0x170..0x188]`；pbuf 数据读 0；trap 内 store 不共享；
- 当前配置 `0317=0x1`、`launch=0x8`；
- 3090 sm86 论文 L3 跑通（230–241 µs，`bad=0`）；
- 去 shim 退化到 6–40 ms。

### 平台约束（由实验穷尽得出）

- sm120/595 上不存在"停住且可恢复"的纯 RM 状态；
- pbuf 无用户态写入口（五类通道已排除）；
- trap 上下文数据读通路整体不通（三分类已定稿）；
- 恢复必须由调试器 agent 完成。

### 未验证 / 推断

- sm120 硅片是否原生支持 regops（未证明不支持）；
- GSP 固件层是否有等价的带内入口（未逆向）；
- 595 装到 Ampere、GSP off 两个控制组（未做）；
- 多 kernel/多队列下的选择性抢占（未测）；
- 0x8 是否在所有配置下都代表 launch trap（当前配置成立，跨配置未证）。
