# 04 第二条结论：GDB / 0317 作为 sm120 的替代形态

> 日期：2026-10-27　事实基线：`FINDINGS_ZH.md` §1–§54（2026-10-27）
> 承接：`report/03-核心结论.md`（第一条结论：595/Blackwell 关闭了用户态可达的 reg-op，
> 论文的 queue-based 带内 L3 在当前 sm120/595 配置下不可实现）
> 本文回答：**既然论文入口不可用，我们实际能做什么？这些替代形态的边界、代价和调度含义是什么？**

---

## 0. 结论（精确版）

**在不打开驱动闸门、不修改驱动的前提下，我们在 sm120/595 上验证了两条可用的 L3 替代路径：**

| 路径 | 一句话 | 关键数字 |
|---|---|---|
| **GDB backend** | cuda-gdb attach 把**整个进程/context** 冻住，detach 后**原地恢复** | 冷冻结 **116 ms**（预热后 103–106 ms：attach 23 + CILP 80）；恢复 8–10 ms；handover 0.73–0.74 s |
| **RM 0317** | 调试器会话让驱动**取消/挂起 context**；被杀 kernel 由 **XQueue 重放** | 设备停 **0.204 ms**；`Suspend` 返回 **22.9–30 ms**；kill 8 s → **0.234 s** |

**但这不是"论文 L3 的等价实现"**：

- 没有带内按 queue 触发；
- 没有 32 µs；
- 0317 **不能原地恢复**（寄存器现场丢失，必须重放）；
- GDB 是 **suspend/resume**（不是 abort+restart），且依赖 cuda-gdb；
- 两者都是 **context/process 级**，不是 hwQueue 级；
- 显存不释放、host 进程在 GDB 下被 ptrace 停住。

**准确表述**：

> **它们是"结果层"的 L3 替代形态（停住 / 让渡 / 恢复或重放 / 结果正确），
> 不是"机制层/性能层"的等价物；适合粗粒度、低频、可重放的场景。**

## 1. 与第一条结论的逻辑衔接

`report/03` 的结论是：

```
论文 L3 = 带内写控制寄存器 + 普通上下文 handler + handler 内 abort
        ↑
595/Blackwell 关闭了 user→kernel 的 reg-op（pGpu+0x911）
        ↓
入口不可用
```

自然的问题：**那还能不能抢占？**

- 如果"抢占"指的是"**让运行中的工作停下、把 GPU 让给别人、之后再继续/重跑**"，
  那么答案是可以——只是换了两条**带外**路径；
- 如果"抢占"指的是"**论文的 32 µs、按 queue、handler 内 abort**"，
  那么在当前配置下不可以（见 `report/03`）。

所以第二条结论不是"我们复现了论文"，而是"**我们找到了两条可用的替代形态，
并量化了它们与论文的差距**"。

## 2. 两条替代路径的机制

### 2.1 GDB：调试器 attach = 冻结 / detach = 恢复

```
l3ctl / xcli l3 / GdbInterruptContext
  └─ cuda-gdb（MI2 子进程）
       ├─ ptrace attach 目标进程（目标需 PR_SET_PTRACER_ANY / 权限）
       ├─ libcudadebugger / cudbgApi 把 CUDA context 切到调试器管理
       ├─ -target-attach → 驱动在安全点停住 context，保存 CILP
       └─ -target-detach / -exec-continue → 恢复 CILP，继续执行
```

- **不需要我们的 handler/cave**；停 context 是 cuda-gdb + 驱动调试 API 的能力；
- 目标进程**不需要改代码**，只需要允许被 ptrace；
- 冻结对象是**进程 + 其 CUDA context**；同一 context 的所有 stream/kernel 一起停；
- host 线程被 ptrace 停住（stop-the-world）；
- 恢复是 **CILP restore**，bit-exact（v0.6）。

### 2.2 0317：RM 调试器 suspend = 取消/挂起

```
target（应用）: CUDA context / compute object
   └─ 0xd04 把 {client, compute} 共享给 agent
agent（独立进程）: 自己的 RM client + 完整 libcuda 初始化
   ├─ 0x83de 会话（绑定 target client + compute）
   ├─ 0x83de031f / 0307 / 032a 等 modes
   └─ 0x83de0317（suspend）→ 驱动/GSP 取消/挂起 target context
```

- **不需要我们的 cave 来停 context**；停/取消是 RM/GSP 的 context 级操作；
- 驱动自己的 trap handler 可能参与 save/pause 路径，但那是驱动内置的，不是我们的 patch；
- **target 自己的 session 发 0317 是 no-op**，必须外部 agent + 0xd04 共享；
- 0317 可能阻塞到 resume，需要应答者（cuda-gdb/调试 agent）。

#### 2.2.1 0317 的四种语义（同一发命令，四种结果）

| context 状态 | 0317 结果 | 观测 | 调度含义 |
|---|---|---|---|
| **普通 CUDA context** | **benign trap** | 签名 `0x5aa5`、`reason=0x1`，内核继续 | 不能当"停机"用 |
| **受管 + `InstrMemAllocator`（默认）** | **context 级 cancel** | `XQueueSuspend` 27–30 ms，stream 判完成 | 适合 kill+replay；丢在飞工作 |
| **受管 + `NO_ICTX_INSTRMEM`** | **no-op** | status 0，计数继续 | 不能停 |
| **CUDA init 前外部 tracer**（strace/plain gdb） | **park** | 计数冻结、`Synchronize` 不返回 | 可停，但**不可释放** |
| **cuda-gdb 应答** | cancel（27.3 ms） | 调试器解掉阻塞 | 调试器路径 |

**解读**：

- 同一个 `0317{1,0}`，结果由 **context 状态 + 谁在应答** 决定；
- 这不是"0317 有时好有时坏"，而是"0317 本身是调试器协议，RM 只是转发"；
- 调度器必须先知道自己在哪个状态：
  - 走 **cancel** → 只能 kill+replay；
  - 走 **park** → 只能 stop-only；
  - 走 **NO_ICTX** → 什么都停不了；
  - 普通 context → 只有 benign trap。

**重要区分：cave 执行 ≠ cave 有决策权。**
在受管 + `InstrMemAllocator` 下，`TRAP_CAVE` + arm-at-Trigger + lazy session + cuda-gdb ack
的配置里，cave 确实在 0317 trap 执行（记录页 `R2=0x1`，`exp_arm_sentinel_host.log`），
但驱动仍然 cancel 并在 resume 时重放（`trap reactivate: replaying the killed kernel`）。
所以不要把"探针能执行"当成"能阻止 cancel"；cave 只能观察/记录/杀 warp，
不能改变驱动对 context 的 cancel/suspend。

证据：`report/02` §4.2；`exp_sig_rm0317.log`、`exp_managed_spin1.log`、
`exp_no_ictx_instrmem.log`、`exp_strace_park1.log`、`exp_gdb_cancel1.log`、
`exp_arm_sentinel_host.log`。

#### 2.2.2 park 入口与"不可释放"

**park 的入口不是 0317 本身，而是"CUDA init 前进程已在外部 tracer 下"：**

- `strace -f`、plain `gdb` 都可以；**不需要 cuda-gdb**；
- 在这种状态下再发 0317，内核才会真正 park（计数冻结、`Synchronize` 不返回）；
- 没有这个前置，0317 在受管 context 上是 cancel 或 no-op。

**park 的表现**：

- 计数完全冻结；
- `cudaStreamSynchronize` 不返回，进程挂住；
- 显存不释放（context 还在）；
- **0318 在 app 自己的 session 和 agent 的 session 上都阻塞**；
- 对已 park 的上下文再次 attach 会挂死（rc=124）；
- 没有用户态释放路径。

**⇒ park 只能作为 stop-only**：

- 适合"先停住、再决定"（例如观察、取证、迁移前暂停）；
- 不能作为"可恢复的 suspend"；要恢复只能：
  - 用 GDB backend（CILP restore），或
  - 放弃这个 kernel，走 kill+replay，或
  - 销毁 context/进程（那就不是抢占）。

证据：`exp_strace_park1/2.log`、`exp_plaingdb_park1.log`、`exp_self_resume1.log`；
完整四态见 `report/02` §4.2。

### 2.3 两者的关系

| 关系 | 说明 |
|---|---|
| cuda-gdb | **0317/0318 + target 侧注入（libcudadebugger）+ CILP 保存/恢复** |
| agent 只发 0317 | 缺 target 侧注入 ⇒ 走 cancel/park，没有 CILP 保存，不能原地恢复 |
| 我们的 cave | 只在 trap 里做 payload（签名/flag/EXIT），**不是停 context 的机制** |
| 论文 | 带内寄存器触发 + 普通上下文 handler + abort；与两者都不同 |

## 3. 停止/恢复语义（逐项）

### 3.1 停什么

| 维度 | GDB | 0317 |
|---|---|---|
| 触发方式 | cuda-gdb attach | RM `0x83de0317` |
| 停止对象 | **进程 + 其 CUDA context** | **context** |
| 同一 context 所有 stream | ✅ 一起停 | ✅ 一起 cancel/park |
| host 线程 | **ptrace 停住** | 不停（可能阻塞在 `Synchronize`） |
| 其他进程 | 不受影响 | 不受影响 |
| 单 stream / 单 queue 选择 | ❌ | ❌ |

### 3.2 资源让出

| 资源 | GDB | 0317 |
|---|---|---|
| SM / 执行资源 | ✅ 让出（v0.7：B 33.65 s → 0.74 s） | ✅ cancel 释放；park 停住（SM 让出未单独测） |
| 显存 | ❌ 不释放（624→634 MiB 实测） | ❌ 不释放（context 保留） |
| host 内存 | 进程被停；cuda-gdb ~48 MB RSS；目标 RSS +~19 MB | 进程不停；agent/会话开销小（未精确测） |
| context/句柄 | 保留 | 保留 |
| 队列/命令日志 | 保留（host 侧） | 保留（XQueue） |

### 3.3 寄存器 / malloc / 幂等

| 项 | GDB | 0317 cancel | 0317 park |
|---|---|---|---|
| 每线程寄存器 / PC / 在飞指令 | **CILP 保存**，恢复后原样 | **丢失** | 停住；可恢复性取决于驱动状态机 |
| 局部/全局显存 | 保留 | 保留 | 保留 |
| host `cudaMalloc` | 保留，可复用 | 保留，重放复用 | 保留 |
| device 侧 `malloc` | 保留/可能泄漏 | 保留/泄漏；重放再分配 | 同左 |
| 恢复方式 | 原地 restore | 重放（从头跑） | 无可用释放路径（0318 阻塞） |

**幂等规则**（适用于 0317 重放）：

| 情况 | 幂等？ |
|---|---|
| host `cudaMalloc` + kernel 覆盖写（如 `C=A+B`） | ✅ |
| `atomicAdd` / `sum +=` / 累加全局内存 | ❌ 重放重复累加 |
| kernel 内 device `malloc`/`free`、依赖指针值 | ❌ 通常不幂等（堆状态/泄漏/地址变化） |
| 随机数 / 时间 / 外部输入 | ❌ |
| 只写固定输出缓冲、覆盖写 | ✅ |

**结论**：**host 侧 `cudaMalloc` 本身不破坏幂等；device 侧 `malloc`、累加、随机、外部状态才是红灯。**
论文只抢幂等 kernel，就是为了能安全地从头重跑。

### 3.4 恢复：CILP restore vs XQueue 重放

| 路径 | 恢复动作 | 主语 | 说明 |
|---|---|---|---|
| GDB | `detach` / `continue`，CILP restore | cuda-gdb/驱动 | 原地续跑，bit-exact；8–10 ms / 1–3.5 ms |
| 0317 + XQueue | **重新提交 kernel（从头跑）** | **XQueue（XSched）** | `trap reactivate: replaying the killed kernel`；0.234 s standalone |
| 0317 单独 | 0318 | 驱动/调试器 | 0318 是调试器状态恢复，**不是重放**；agent 路径常阻塞 |
| park | 无 | — | 0318 不可释放；进程可能卡住 |

**关键**：

- **"重放"的主语是 XQueue，不是 GPU**；
- 重放 = **new launch**（重新提交命令），不是"从原 PC 继续"；
- 0318 ≠ 重放；0318 只是退出 suspend 状态；
- 如果没有 XQueue（standalone `l3x` kill），**没有自动重放**，脚本只负责杀；
- 重放要求 kernel 幂等；非幂等结果可能错。

## 5. 适用场景与不适用

| 场景 | GDB | 0317 | 论文 |
|---|---|---|---|
| 整进程/context suspend/resume | ✅ 116 ms | ❌（不能原地） | ❌（abort+重跑） |
| 让渡 GPU 给其他任务 | ✅（33.65→0.74 s） | ✅ cancel/park | ✅ |
| 幂等 kernel abort + 从头重跑 | ⚠️ 可做但非其语义 | ✅ 0.234 s | ✅ 32 µs |
| 按 queue/stream 选择目标 | ❌ | ❌ | ✅ |
| 32 µs 级延迟 | ❌ | ❌ | ✅ |
| 无调试器/无 agent 部署 | ❌ | ❌ | ✅ |
| 调试/正确性验证 | ✅ | ⚠️ | ⚠️ |

**适用**：粗粒度、低频、可重放/可暂停的负载；批处理、长 kernel、调试；
**不适用**：延迟敏感、需要 per-queue 选择、需要原地恢复、不能依赖调试器的生产环境。

## 6. 条件/配合清单

### GDB

| 条件 | 说明 |
|---|---|
| cuda-gdb 安装且与驱动/GPU 匹配 | 595 可用 |
| 目标允许 ptrace | 同 uid/root；`PR_SET_PTRACER_ANY`；容器需 CAP_SYS_PTRACE 或目标自开 |

| 条件 | 说明 |
|---|---|
| target 0xd04 共享 | 把 client/compute 共享给 agent |
| agent 独立 client + 完整 libcuda | target 自己的 session 是 no-op |
| 0x83de 会话 | 绑定 target client + compute |
| 应答者 | 0317 可能阻塞到 resume |

## 8. 反方观点与常见误读

| 误读 | 回应 |
|---|---|
| "0317/GDB 复现了论文 L3" | 没有。结果层替代，机制/性能不等价；没有 32 µs/per-queue。 |
| "装了 gdb 就能冻结所有 kernel" | 只停目标进程；需 ptrace 权限；短 kernel 可能跑完；受保护进程不行。 |
| "0317 能冻结所有 kernel" | 不是；四种语义取决于 context 状态，需要会话/共享/应答。 |
| "冻结/取消后显存会释放" | 不会；context 还活着，显存保留；只有 destroy/exit/free 才释放。 |
| "有 malloc 就不幂等" | host `cudaMalloc` 不破坏幂等；device `malloc`/累加/随机才是红灯。 |
| "0318 是 resume，所以能原地恢复" | 0318 是调试器状态恢复；agent 路径没有 CILP 保存，实际靠 XQueue 重放。 |
| "cave 停了 context" | cave 只是 trap 里的 payload；停 context 靠 cuda-gdb/驱动或 RM 0317。 |
| "27 ms 就是停的延迟" | 不是；设备 0.204 ms 就停了，27 ms 是 `Suspend` 返回/收尾。 |

## 9. 可证伪条件

1. 在 0317 路径上找到一种能保存并恢复 CILP 的用户态方法
   ⇒ "不能原地恢复"不成立；
2. XQueue 对非幂等 kernel 的重放仍能得到正确结果（有通用机制）
   ⇒ "只支持幂等 kernel"需要修正；
3. GDB 冻结在多租户/满负载下无法让出 SM（handover 失败）
   ⇒ G1/G2 需要限定条件；
4. 0317 能按 queue/stream 选择性停（而不是 context）
   ⇒ "context 级"需要修正；
5. 5090 上 managed kill 复现 0.234 s
   ⇒ T5 从"未达成"变为"已达成"。

## 10. 我们发现的"新调度模式"

综合两条替代路径，实际可用的调度模式是：

> **带外、调试器辅助、context/process 级、可暂停或可重放的抢占。**

它不是论文的 queue-based 32 µs，而是一套**工程契约**：

| 契约 | 内容 |
|---|---|
| **抢占单元** | GDB：进程/context；0317：context；**不是 hwQueue** |
| **延迟预算** | GDB ~106–116 ms；0317 ~23–30 ms；**不是 32 µs** |
| **语义** | GDB：suspend/resume（bit-exact）；0317：abort + 从头重跑 |
| **恢复** | GDB：CILP restore；0317：XQueue 重放；0318 不是重放 |
| **内存** | 显存不释放；host 预分配复用；**避免 device 侧 malloc** |
| **幂等** | 0317 重放要求幂等；避免原子累加/随机/外部状态 |
| **依赖** | cuda-gdb / 0x83de 会话 + 应答；不是"无调试器生产部署" |
| **适用** | 粗粒度、低频、长 kernel、可暂停/可重放；批处理、调试、handover |

**这套模式的定位**：

- 对"能不能抢占"：**能**；
- 对"论文的 32 µs / per-queue"：**不能**；
- 对"生产部署"：GDB 可作为**可用的 fallback**；0317 更适合**kill+replay**；
- 对"研究"：它是**替代形态**，真正的论文路径仍需开闸/调试 agent/换平台。

## 11. 汇报口径（一页）

| 项 | 内容 |
|---|---|
| 第二条结论 | GDB（116 ms suspend/resume）与 0317（27 ms cancel/kill+replay）是结果层替代，不是机制/性能等价 |
| 证据 1 | GDB：attach 23 + CILP 80 = 106 ms；恢复 8–10 ms；handover 33.65→0.74 s；bit-exact |
| 证据 2 | 0317：设备停 0.204 ms；`Suspend` 返回 22.9–30 ms；kill 0.234 s；四种语义 |
| 证据 3 | 寄存器：GDB CILP 保存；0317 cancel 丢失；重放由 XQueue 重新提交 |
| 证据 4 | 显存不释放；host cudaMalloc 可幂等，device malloc/累加是红灯 |
| 边界 | context/process 级、无 per-queue、无 32 µs、依赖调试器 |
| 下一步 | 开闸（P1）、第二入口（P3）、调试 agent（P4c）、换平台（P6） |

**一句话**：

> "论文入口被关之后，我们没有硬造一个 32 µs 的假象；我们做了两条真实可用的替代路径：
> GDB 能冻结/恢复整个进程（116 ms、bit-exact、让出 SM、显存不释放），
> 0317 能让 context 停/杀并由 XQueue 重放（27 ms、0.234 s kill）。
> 它们是结果层的 L3，不是论文的机制/性能等价；这也定义了 sm120 上新的调度契约。"
