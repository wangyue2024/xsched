## 0. 汇报摘要

**一句话**：sm120 上已经有可用的 Level-3（GDB backend）与可复现的 trap 原语；
trap-native 的"停住且原地恢复"仍不可达，根因是**中断入口被 595 驱动在启动期关闭**，
以及**请求/目标与恢复都归调试器状态机所有**，不是 handler 不会执行。

| 结论 | 状态 | 关键数字/证据 |
|---|---|---|
| 生产可用 L3（能停能恢复） | 已交付 | GDB backend：设备静止 116 ms、attach ~23 ms、handover 0.73–0.74 s、`Resume=1` |
| trap 注入与 kill | 已打通 | 活体 handler 签名 `0x5aa5`；8 s 内核 → 0.234 s、`cudaSuccess` |
| 受管内核 trap 停住 | 已打通 | 27–30 ms cancel；设备真正冻结 0.204 ms；park 可亚毫秒停 |
| kill + 队列重放 | 已闭环 | 受管 launch 记录→重放；裸 `EXIT` 会破坏重放（v6.8） |
| 判据（事件区分） | 部分 | 当前配置 `0317=0x1`、`launch=0x8`；只分事件，无 target |
| 判据（选择目标 kernel） | 未达成 | 缺 per-suspend target ID 与 request 的 host→trap 通道 |
| 原地恢复（trap-native） | 未达成 | `0318` 在所有 client 阻塞；只有调试 agent 能恢复 |
| 论文方法复现 | sm86 成功 / sm120 不可 | sm86 `level 3` p50 230–241 µs；sm120 regops 被 `pGpu+0x911` 关闭 |

## 2. 论文基线（OSDI'25 原文）

论文（XSched, OSDI'25）对 Lv3 的定义与实现要点（§4.3 / §6.2 / §6.3 / §7.3）：

1. **目标**：中断正在执行的命令，达到"超低且稳定"的抢占延迟；被中断的命令之后恢复。
2. **两条实现**：
   - **TSG-based**：调 TSG timeslice，进程级，粒度粗；
   - **Queue-based（论文主路径）**：发现一条**写 GPU 控制寄存器的 ioctl**，
     GPU 立即 stall 所有运行 kernel，调用 trap handler 保存上下文并**检查 trap reason**；
     XSched 扩展 handler 识别"自己触发的中断"，命中则 abort 目标 kernel，其余 restore 继续。
3. **信息交互两条独立通道**（§47 已核对，不是"handler 读全局 flag"）：
   - Lv2 guardian：per-hwQueue deactivation flag 在 GPU global memory，
     由注入 kernel 头部的 guardian（普通 kernel 上下文）读取；
   - Lv3：**"信息"就是 trap reason 本身**，无 host→handler 数据 buffer。
4. **恢复语义**：GPU 不支持断点恢复，Lv3 **只抢幂等 kernel 并从头重跑**。
5. **延迟**：T=0.5 ms 时，Lv1 P99≈8T、Lv2≈1T、**Lv3 P99 = 32 µs 且与 T 无关**（GV100）。
6. **平台**：queue-based 实现在 Volta 与 Ampere（GV100 / Ampere 300 余行）。

### 3.4 判据与输入（v6.5–v6.8 最新）

**handler 可读的 launch 固定参数（实测）**：

| 常量库偏移 | 值（受管 launch 实测） | 含义 |
|---|---|---|
| `c[0x0][0x170]` | `0x02000000` | XSched preempt buffer 指针低 32 位 |
| `c[0x0][0x178]` | `0xb6c00200` | guardian entry 低 32 位 |
| `c[0x0][0x180]` | `0x1` | `kernel_idx = 1`（与队列 `remembered idx=1` 一致） |
| `c[0x0][0x188]` | `0x1` | `killable = 1` |

**trap 可读地址三分类（v6.7 定稿）**：

| 类别 | 地址/来源 | 结果 |
|---|---|---|
| 读到有效数据 | `c[0x0][0x170..0x188]`、`SR`（reason）、local stack | 可用 |
| 不 fault 但恒 0 | 自建 `cuMemAlloc`、XSched preempt buffer、host-mapped UVA；**0317 陷阱里的驱动 pbuf** | 0 |
| fault（700） | 代码页、描述符 `LDG`、launch trap 时的 pbuf（已重定位）、scratchpad 盲访 | 不可用 |

**reason 判据（v6.8）**：

| 事件 | `R2` | 说明 |
|---|---|---|
| `0317{1,0}` | `0x1` | 当前配置稳定 |
| 设备 writer 内核的 launch trap | `0x8` | 与 0x1 不同 |
| 边界 | 0x8 不保证跨配置；应按**精确值** `R2==0x1` 门控，并在目标配置复验 launch reason |
| 局限 | 只区分"事件"，**不含 target**；单队列够用，多 kernel 选择仍无解 |

**驱动 pbuf 的请求/目标通道（v6.6/v6.8 已关闭）**：

- `0317` 陷阱里 `pbuf+0/+4/+8` **全 0**（地址 `base−0x8000000`，可读不 fault）；
  `R2=0x1` 而非 cmd=2 应得的 `0x30`，说明驱动自己读到的命令字也是 0；
- 在 `0317` 陷阱里对 `pbuf+4` 发 `ST.E`：**不 fault**，但写 1/写 2 行为完全相同，
  **store 不进入驱动可见的 pbuf**（像是私有/快照映射）；
- 结论：pbuf 不能做 host→trap 的 request/target 通道；cmd=2/idx 只属于真调试器 suspend。

## 6. 能力边界：0317 的三种语义

同一发 `0317` 在 sm120/595 上取决于上下文状态：

| 上下文状态 | 0317 的结果 | 证据 |
|---|---|---|
| 普通 CUDA 上下文（l3x） | benign trap：进 handler（签名/reason 0x1），内核继续 | `exp_sig_rm0317.log` |
| 受管 + `InstrMemAllocator`（默认） | **context 级 cancel**（27–30 ms，stream 判完成，丢在飞工作） | `exp_managed_spin*` |
| 受管 + `NO_ICTX_INSTRMEM` | **no-op**（status 0，但不停） | `exp_no_ictx_instrmem.log` |
| 受管 + CUDA init 前外部 tracer | **park**（停住、`Synchronize` 不返回，不可释放） | `exp_strace_park*`、`exp_plaingdb_park1.log` |
| 受管 + cuda-gdb agent 应答 | cancel（27.3 ms） | `exp_gdb_cancel1.log` |

**不存在"停住且可恢复"的 RM 状态**（§27/§30/§46）。

## 7. 根因链（四道锁）

```
① 触发锁：0x419e84 / cuXtraTriggerTrap
   -> pGpu+0x911 启动期能力位 = 0
   -> 0x20800122 在闸门处 return NV_OK（跳过写）；0x83de031d 返回 0x56（静默 no-op）
   -> 只剩 RM 0317 debugger-suspend

② 请求/判据锁：0317 的 reason
   -> 旧结论"恒 0x1 不可区分"
   -> v6.8：当前配置 0317=0x1、launch=0x8，事件可分
   -> 但仍无 per-suspend target ID；0x8 不保证跨配置

③ 输入/目标锁：handler 的输入
   -> 能读 c[0x170..0x188]（preempt_buf/guardian/kernel_idx/killable）
   -> pbuf 数据在 0317 陷阱里全 0；trap 内 store 不共享
   -> host 无写入口（cuXtra 运行期 invalid、设备 store 非法、CPU 零页）
   -> 无法告诉 handler "这次要杀哪个 kernel"

④ 恢复锁：0318 / 调试器状态机
   -> 0318 在所有 client 阻塞
   -> 0317 是通道级挂起 + 队列重放，不是 CILP 原地恢复
   -> 裸 EXIT 破坏驱动 trap 状态机，重放失败
   -> 恢复只能由 libcudadebugger 的进程内 agent 完成
```

**结论**：论文式 L3 依赖"带内、可识别来源的中断"；sm120/595 上这条入口被软件关闭，
替代品（0317）又不能提供 target/request 与原地恢复。27 ms/116 ms 是结果，不是根因。

## 9. A/B 三段耦合

快路径不是"触发"一件事，而是三段缺一不可：

```
managed launch（shim / debugger params）
  + instrumented handler（+0x3e0 / +0x880）
  + 带内触发（0x20800122 -> 0x419e84）
```

| 平台 | managed launch | handler | 触发 | 结果 |
|---|---|---|---|---|
| 3090 sm86/570 | 有 | 有 | 有 | **230 µs**，正确性 OK |
| 3090 去 shim | 无 | 有 | 有 | 6–40 ms |
| A100 sm80/550 | cuxtra 崩 | 有 | 有 | 带 shim 不可用；无 shim 33–55 ms |
| sm120/595 | 有 | 有 | **无** | 0317 27 ms / GDB 116 ms |

**架构 vs 驱动**：同一套上游代码在 sm86/570 上跑通，说明不是"Blackwell 不支持 trap"；
差别落在 595 对 sm120 关闭了 regops 能力位。尚未隔离的控制组：595 装到 Ampere、GSP off。

## 11. 下一步与决策建议

| 目标 | 建议 | 代价 |
|---|---|---|
| 尽快可用 | 维护 GDB backend，预热 cuda-gdb；接受 116 ms 设备静止下限 | 低 |
| 摆脱 cuda-gdb | 实现/复用 `libcudadebugger` 进程内 agent（`DebugAgentMain` + `cudbgApi*` + preemption-buffer accessor） | 高（协议/注入/映射） |
| 快速 park-only | 自写 PTRACE_SEIZE 守护 + 0317（不恢复） | 低，但语义受限 |
| 论文复现 | 换 sm86/570（已验证）或 GV100/sm70（原始 32 µs）；sm120 需打开 `pGpu+0x911` | 硬件/驱动成本 |
| 继续 trap-native 研究 | 唯一缺口是 **target ID + request 的 host→trap 通道**；pbuf 通道已关闭，候选只剩调试 agent 或 GSP RPC | 高 |

**建议**：如果交付优先，锁定 GDB backend；如果研究目标必须 sm120 trap-native，
把资源集中到进程内调试 agent（唯一纯用户态路径），不要继续在 RM 命令里找 mailbox。

## 12. 风险与边界

- 不要盲写 GPU 寄存器/BAR0：本机显示与计算共用 GPU，未知寄存器可能挂死。
- 不要 `rmmod` / 重载驱动：会中断显示与所有 CUDA 进程，需要明确授权。
- 驱动版本敏感：所有偏移/指纹只对 595.99.02 有效。
- 会话有副作用：`0x83de` 会话会改变 launch/代码写行为；用完释放。
- 证据标准：任何"停住"必须同时满足计数冻结、`Synchronize` 状态、host 回读一致。
- 多处结论曾被后续实验更正（`NO_PATCH` 语义、launch trap、reason 恒 0x1、
  "trap 上下文 ST 写 pbuf 必 700"），引用时以 FINDINGS 最新章节为准。

**v6.8 口径更正**：`trap 上下文 ST.E 写 pbuf 会 700` 只对 **launch trap** 成立；
在 `0317` 陷阱里 store **不 fault**，但写入不与驱动共享，行为上无效。
