# 02 中断入口：从"带内、按 queue、正常内核上下文"到"带外、context 级、debugger-suspend 上下文"

> 日期：2026-10-26　事实基线：`FINDINGS_ZH.md` §1–§54（2026-10-27）
> 本文只回答一个问题：**"中断入口换了"这个判断，证据链是什么？哪些是实测、哪些是论文原文、哪些是推断？**
> 结论先行：三句话都成立，但"按 queue"要分两层说——**硬件 stall 是全局的，XSched 的
> 目标选择是 hwQueue 粒度（靠 preempt buffer 记账）**；sm120 上这两层都不成立：
> stall 退化为 context 级，preempt buffer 里也没有目标。

---

## 0. 先把观点拆成可检验的子命题

原句包含三个独立主张，必须分开取证：

| 编号 | 子命题 | 检验方法 | 置信度 |
|---|---|---|---|
| **A** | sm86/Volta 是**带内**触发（写 GPU 控制寄存器）；sm120 只剩**带外** RM `0317` | 代码 + 论文 + 动态副作用 | A1/A2 高；A3 中（"带内"定义见 §1） |
| **B** | sm86 的目标选择是**按 hwQueue**；sm120 的 `0317` 是**context 级** | 论文 + payload 源码 + 四态实验 | 高（B2 的"per-queue"是软件记账粒度，非硬件 stall 粒度） |
| **C** | sm86 的 handler 在**正常内核上下文**；sm120 的 handler 在 **debugger-suspend 上下文** | 全局读写实验 + payload 行为 + 恢复语义 | 高 |
| **D**（推论） | 因此 **request/target 通道**与**恢复所有权**一起转移到了调试器 | 由 A–C 推出，再用 pbuf/0318/EXIT 实验验证 | 高 |

**术语定义**（避免"带内/带外"歧义）：
- **带内**：host 通过正常驱动控制路径**直接写 GPU 控制寄存器**，不建立调试器会话；
  硬件中断把 trap 送进**正常内核上下文**的 trap handler。
- **带外**：host 通过 RM `0x83de` **调试器命令**让驱动/GSP 挂起上下文；
  trap 发生在**调试器管理的 suspend 上下文**里。

## 1. 论文原文（sm86/Volta 的设计基线）

OSDI'25 §6.3（p.679）原文要点：

> "**Queue-based preemption.** We devise the first fine-grained interrupts on NVIDIA GPUs
> to implement Lv3 preemption **at the hwQueue granularity**. ... we discovered a specific
> **ioctl that triggers GPU interrupts by writing to a GPU control register**—a feature
> originally intended for kernel debugging. When the GPU is interrupted, it immediately
> **stalls all running kernels** and invokes the **trap handler to save context and check
> trap reason**. ... XSched extends the trap handler to **detect interrupts triggered by
> XSched**. When detected, the **target kernel is aborted** for preemption, and the rest
> ones restore the context and continue execution."
>
> "... XSched only preempts **idempotent kernels and restarts them from the beginning**."

原文同时说明：Lv3 的 queue-based 实现落在 **Volta 与 Ampere**；TSG-based 落在 Pascal 之后。

**这里必须拆开两层**：
1. **硬件 stall 范围是全局的**（"stalls all running kernels"）；
2. **XSched 的目标选择是 hwQueue 粒度**（"at the hwQueue granularity"），
   靠的是 trap handler 读 **preempt buffer** 里的 `global_exit_flag` / `preempt_idx`，
   再和**当前 kernel 的 `kernel_idx`** 比较。论文没有"host 写 target ID"这一步。

## 2. sm86/570：子命题 A/B/C 的正向证据

### 2.1 代码路径：触发确实是 `cuXtraTriggerTrap`（写控制寄存器）

| 证据 | 位置 | 说明 |
|---|---|---|
| 触发调用 | `platforms/cuda/hal/src/level3/interrupt.cpp:105` | `Interrupt()` → `cuXtraTriggerTrap(kCtx)` |
| 接口声明 | `3rdparty/cuxtra/include/cuxtra/cuxtra.h:152` | `CUXTRA_FUNC void cuXtraTriggerTrap(CUcontext ctx);` |
| 论文机制 | OSDI'25 §6.3 | ioctl 写 GPU 控制寄存器 → 全局 stall → trap handler |
| sm120 上的对照 | `arch.cpp` / `interrupt.cpp` 注释 | sm120 不再调用它，改走 `TrapSm120Context::Trigger()` |

### 2.2 handler payload：**读写全局内存**，并按 `kernel_idx/preempt_idx` 选目标

上游注入源码 `platforms/cuda/hal/inject/inject.cu`（sm86/sm120 共用同一算法）：

```c
// 布局（line 47）：
// | global_exit_flag | reserved | preempt_idx(64) | exit_flag_block0 | restore_flag_block0 | block1 ... |
INJECT_FUNC void check_preempt_trap(uint32_t *preempt_buffer_addr, ...)  // line 91
{
    if (!idempotent || *global_exit_flag == 0) goto out;   // 读全局
    preempt_idx = *preempt_idx_ptr;                        // 读全局
    if (preempt_idx == 0) goto save_preempt_idx;
    if (preempt_idx == kernel_idx) goto save_restore_flag;
    exit();                                                // 别的 kernel 在抢占
save_preempt_idx:
    *preempt_idx_ptr = kernel_idx;                         // 写全局
save_restore_flag:
    *block_restore_flag = 1;                               // 写全局
    exit();
}
```

编译后的 SASS 在 `platforms/cuda/hal/src/arch/sm86.cpp:198`（`trap_inject_instrs`）
与 `arch/sm120.cpp:154`（同算法重生成）。sm120 版本带注释，明确是：

```
LDC R4/R5, c[0x170/0x174]   // preempt buffer 指针
LDC R6/R7, c[0x180/0x184]   // kernel_idx
LDC R8,    c[0x188]         // killable
LD.E R0,[R4]                // global_exit_flag
LD.E.64 R8,[R4+8]           // preempt_idx
ST.E.64 [R4+8],R6           // 存我的 kernel_idx
ST.E [R4+4+...],R7          // block_restore_flag
EXIT
```

**这条证据同时证明 A/B/C 三件事**：payload 在 trap 里做**全局读写**（正常上下文），
用 `preempt_idx == kernel_idx` 做**目标选择**（按 hwQueue/命令记账），
并且 host 只写一个 flag，不写 target。

### 2.3 A/B 实测：同一套代码在 sm86/570 上跑通

| 配置 | 结果 | 证据 |
|---|---|---|
| 3090 sm86/570，`level 3`，带 shim | **p50 230–241 µs**、p99 0.42–2.8 ms、restore 93–127 µs | `evidence/ab_ampere/battery_3090/level3_{1,2,3}.log` |
| 正确性 | 200 次 suspend/resume 后 16M 元素 **bad=0** | `evidence/ab_ampere/correct_sm86.log` |
| 去 shim | 退化到 **6–40 ms** | `evidence/ab_ampere/level3_sm86_noshim.log` |
| handler 实物 | 0x1200；`+0x3e0` = `IADD3 R1,R1,-0x10,RZ` | `sm86_handler.bin`、`sm86_handler_dump.log` |
| 触发序列对照 | cuda-gdb 走 `0307→0317→0315/030c/0316→0318`，与 `cuXtraTriggerTrap` 是两条路径 | `sm86_agent_ioctl_0317.log` |

**这张表回答"是不是架构问题"**：同一套上游代码、同一套 payload、同一台 GPU 上
没有调试器会话，`level 3` 仍能到 229 µs 且结果 bit-correct ⇒ **sm86 的入口和上下文
就是论文描述的那条**；sm120 的失败不能归因于"Blackwell 不支持 trap"。

### 2.4 B 的边界（诚实标注）

- "at the hwQueue granularity" 是**论文的表述 + payload 的记账方式**；我们**没有**
  单独做"多 hwQueue 同时运行、只 abort 其中一个"的隔离实验。
- 我们验证的是单 stream、单 kernel 的 kill/replay；**多 kernel 选择性未实测**（§51 也注明）。
- 硬件 stall 本身是全局的（论文原文），所以"按 queue"指的是**目标选择粒度**，
  不是"只 stall 那个 queue"。

## 3. sm120/595：子命题 A 的反向证据（带内入口不可用）

### 3.1 静态证据：`pGpu+0x911` 是启动期能力位

`FINDINGS v1.1`（§1）对 `nv-kernel.o_binary` 全 `.text` 扫描：

```
0x17376  movb $0x1,0x911(%rdi)   __nvoc_init_dataField_OBJGPU+0x546
0x17b4c  movb $0x0,0x911(%rdi)   __nvoc_init_dataField_OBJGPU+0xd1c
```

- **全二进制只有这两处写 `0x911`**，都在 OBJGPU 的构造/初始化路径（驱动加载或 GPU attach 时执行一次）；
- 读点就在两条 reg-op 通路上：`ksmdbgssnCtrlCmdDebugExecRegOps_IMPL@0x21a990`、
  `subdeviceCtrlCmdGpuExecRegOps_cmn@0x2dcfc0`；
- 闸门为 0 时，两条 reg-op 路径的处理不同，但**都不执行寄存器操作**：
  - **subdevice**（`0x20800122`）：`subdeviceCtrlCmdGpuExecRegOps_cmn@0x2dcfc0`
    在 `0x2dd122` 做 `cmpb $0x0,0x911(%r12); je → 2dd02a`，返回 **NV_OK**，
    跳过后面真正的寄存器写；
  - **会话**（`0x83de031d`）：`ksmdbgssnCtrlCmdDebugExecRegOps_IMPL@0x21a990`
    在 `0x21a9cc` 做 `cmpb $0x0,0x911(%rbx)`，为 0 时直接返回 **0x56**（不是 NV_OK），
    根本不进入执行分支。
- **`0x419e84` 这个寄存器地址不在 nv-kernel 里**：按字节扫描
  （`84 9e 41 00`）只出现在 `libcuda.so.595.99.02`（多处）和
  `3rdparty/cuxtra/lib/libcuxtra_linux_x86_64.a`（2 处），
  nv-kernel **0 处** ⇒ 寄存器地址由**用户态 reg-op 描述符**传入，
  内核里的 handler 是通用的"执行这批 reg ops"，闸门只决定"执不执行"。
- **`0x911` 的写点只有两处**（`0x17376 movb $1`、`0x17b4c movb $0`），
  都在 `__nvoc_init_dataField_OBJGPU`；读点有很多（各调试/reg-op 路径共用这个能力位），
  但**没有运行期 setter**。

**置信度**：这是对 595.99.02 的静态结论；换驱动版本必须重验。运行期无写入点，
不代表别的版本也没有。

### 3.2 动态证据：接口"接受"但无副作用

| 尝试 | 结果 | 证据 |
|---|---|---|
| `0x20800122`（subdevice reg-ops） | 部分返回 0、部分 `0x3a`；寄存器回读仍为 `0`（无有效副作用） | `evidence/live/exp_regops2.log`、FINDINGS v0.3 §7 |
| `cuXtraTriggerTrap`（`0x419e84` bit31） | 立即返回，内核计数 **36.9 M/s 不冻结** | `FINDINGS §v0.2`、`exp_baseline_trigger.log` |
| `0x83de031d`（会话 reg-ops） | 闸门为 0 时返回 **0x56**，不执行寄存器操作 | 反汇编 `0x21a9cc`；FINDINGS v1.1 |
| `brkpt` | 直接杀上下文（不是 trap） | `FINDINGS v1.1` |
| 只写寄存器、不插桩 handler | A100 上内核照跑；sm120 上更不可能 | `FINDINGS §49` |

### 3.3 A/B 反向对照：同一套代码，sm120 触发不了

`FINDINGS §49/§50`：上游 `XpuOS/xsched` 在 3090 上 229 µs；在 sm120/595 上
`level 3` 的 `0x20800122` 被 `pGpu+0x911` 静默跳过，只能 0317（27 ms）或 GDB（116 ms）。

⇒ **子命题 A 的"带内 → 不可用"成立**，且原因是**入口策略**，不是协议/权限/代码错误。

### 3.4 "没发现"还是"不存在"：证明协议

这是本文最需要说清的方法论问题。**"不存在"是一个全称否定，实验无法直接证明**；
我们能做的是把它拆成四层，逐层给出证据，并标明边界。

| 层 | 要证明什么 | 已做的证据 | 还缺什么 |
|---|---|---|---|
| **L1 存在性** | 触发机制在软件栈里**存在** | `0x419e84` 在 libcuda（多处）和 libcuxtra（2 处）；nv-kernel 有 `0x20800122`/`0x83de031d` 的 handler 与 `0x911` 闸门；3090 上同一接口产生 trap | — |
| **L2 可达性** | 我们的进程**能调用到** handler | `0x20800122`/`0x83de031d` 有返回码（0 / 0x3a / 0x56）；`cuXtraTriggerTrap` 立即返回 | — |
| **L3 副作用** | gate=0 时**不执行寄存器操作** | 反汇编：subdevice 在 `0x2dd122` gate=0 → NV_OK 跳过写；会话在 `0x21a9cc` gate=0 → 0x56；动态：PTIMER 回读 0、内核计数 36.9 M/s 不停 | — |
| **L4 因果性** | 差异**来自 gate**，不是别的 | 3090/570 同码 229 µs；sm120 gate 为 0；静态只有两处 init 写、无运行期 setter | **同一台 sm120 上把 gate 打开的反事实实验**（需专用机器/驱动重载） |
| **L5 穷举性** | **没有第二条**用户态可达入口 | 已枚举：RM controls、cuxtra、debugger/0317、tracer、BAR0（不可用/不安全） | 全量 RM control/escape 的副作用矩阵；换驱动版本复扫 |

**关于"是不是 sm120 的地址变了"**：`0x419e84` 在 **550/570/595 三个 libcuda** 里都以
硬编码立即数出现（595 反汇编 13 处，形如 `movl $0x419e84,-0x1c(%rbp)` / `mov $0x419e84,%esi`；
570 上同地址可用），不像"sm120 专属地址"。更重要的是：**gate 检查在真正写寄存器之前**，
地址对不对都轮不到执行。因此"换个地址"不是首选解释；要验证地址假设，必须先有一条
**未被 gate 的写路径**（BAR0/root，当前不可用）或先把 gate 打开。

**因此准确的表述是**：

- **不是"没发现"**：机制、接口、寄存器地址、闸门位置都已定位；不是盲找；
- **也不是"根本不存在"**：机制存在，且在 3090/570 上可用；
- **是"在这台 sm120/595 的启动配置下，用户态可达的触发被闸门关闭"**；
- **"没有第二条入口"目前是经验性穷举**（L5），不是数学证明。要把它升级成更强的结论，
  需要 L4 的反事实实验 + L5 的全量副作用矩阵。

**可证伪判据**（任一成立即推翻/修正"入口被关"）：
1. 在 sm120 上找到运行期写 `0x911` 的路径（换驱动版本/模块参数）并成功写 `0x419e84`，
   内核出现与 0317 不同的 reason；
2. 任何一个用户态可达的 RM control/escape 在不建调试器会话的前提下让运行中内核停住；
3. 直接 mmap BAR0 写控制寄存器成功（需要 root/专用机器，且不在当前安全边界内）。

## 3.5 接口层：`0x20800122` 到底是什么，为什么用不了

### 3.5.1 它不是函数，是一个 RM 命令号

用户态通过通用的 RM control ioctl 调它：

```
ioctl(fd, NV_ESC_RM_CONTROL = 0xc020462a,
      &NVOS54{ hClient, hObject = subdevice,
               cmd = 0x20800122,
               params = &blob(48B), paramsSize = 0x30, status })
```

- 命令名：`NV2080_CTRL_CMD_GPU_EXEC_REG_OPS`（"执行一批寄存器操作"）；
- 内核分发：`subdeviceCtrlCmdGpuExecRegOps_IMPL@0x2dd410`（0x26 B）
  → `subdeviceCtrlCmdGpuExecRegOps_cmn.constprop.0@0x2dcfc0`（0x3a8 B）；
- 48 B 参数块：
  `{hClient, hChannel, hObjectContext, field0c, field10, regOpCount, pRegOps, tail[4]}`；
- `regOps[]` 按 **32 B stride**，每项含 `regOp/regStatus/regOffset/value/mask/shift`；
- 内核先用 `gpuValidateRegOffset` 校验 offset，再决定"执不执行"。

**它不是"写某个寄存器"的专用函数**，而是一个通用的"读/写一批寄存器"入口。
`cuXtraTriggerTrap` 最终就是通过它去写 `0x419e84` 的。

### 3.5.2 为什么写 `0x419e84` 必须经过它

- `0x419e84` 这个字节序列**不在 nv-kernel 里**（0 处），而在
  `libcuda.so.595.99.02`（反汇编 13 处硬编码立即数）和 `libcuxtra.a`（2 处）里；
- 也就是说：**寄存器地址是用户态库构造成 reg-op 描述符传下来的**，
  内核只负责"执行这批 op"；
- 所以"能不能写 `0x419e84`"等价于"能不能让内核执行 reg-op"。

### 3.5.3 五步证据链：写为什么没发生

| 步 | 结论 | 证据 |
|---|---|---|
| ① 用户态可达路径 | 只有 `0x20800122`（subdevice）/ `0x83de031d`（会话）等 reg-op 入口 | `probe/regops.cpp`、`RM_REVERSE_ZH.md` |
| ② 内核在执行前检查 gate | `0x2dd122 cmpb $0,0x911(%r12)`；`0x21a9cc cmpb $0,0x911(%rbx)` | 反汇编（见 §3.6） |
| ③ 本机 gate = 0 | 两处 init 写只置 0/1，初值来自能力位；本机为 0 | `v1.1` 静态扫描 + 动态行为 |
| ④ gate=0 直接返回 | subdevice：`0x2dd120 xor eax,eax` → `je 0x2dd02a` → **NV_OK，跳过写**；会话：`mov $0x56,%eax; ret` | 反汇编 |
| ⑤ 寄存器没被访问 | 读 PTIMER/PMC_BOOT_0 也回 0；`cuXtraTriggerTrap` 后计数继续 | `exp_regops2.log`、`exp_baseline_trigger.log` |

**对照实验（最关键）**：用同一个 `0x20800122` 去读两个"必然非零"的寄存器：

| 寄存器 | 正常应读到 | 实测 | 说明 |
|---|---|---|---|
| `PMC_BOOT_0`（`0x0`） | 非零芯片 ID | **0** | 不是"这个寄存器恰好为 0" |
| `PTIMER_TIME_0/1`（`0x00200510/14`） | 非零且递增 | **0 / 0** | 读操作根本没执行 |
| `read w/ channel` | 非零 | **status=0，value=0** | 控制"成功"但 op 被跳过 → gate 早退的签名 |

如果只是 `0x419e84` 地址不对，PTIMER 读应该正常；它也不正常 ⇒ **坏的是通路，不是地址**。

**证据强度与 caveat**：
- **决定性**：反汇编显示 gate 检查在寄存器访问之前，gate=0 直接返回；
- **支持性**：PTIMER/PMC_BOOT_0 读 0、`status=0` 但 `value=0`；
- **caveat**：`regOps` 结构体是逆出来的，若字段布局仍有偏差，`value=0` 也可能是探针问题；
  但静态分支不依赖结构体，仍是定论。

### 3.5.4 能不能绕过 `0x20800122`

| 绕法 | 做法 | 现状 | 风险 |
|---|---|---|---|
| 换 RM 命令 | `0x83de031d`（会话 reg-ops） | 也检查 `0x911`，为 0 返回 `0x56` | 低，但没用 |
| 换 RPC 变体 | `rpcGpuExecRegOps_v12_01`、`rpcCtrlDbgExecRegOps_v1A_10`、`rpcCtrlB0ccExecRegOps_v1A_0F` | 未验证是否用户态可达/是否都检查 gate | 研究性，未知 |
| 打开 gate | 改模块参数/注册表，让 `0x911=1` 后重新初始化 GPU | 需要 root + 重载驱动 + 专用机器 | 中高 |
| 改驱动 | patch 掉 gate 检查或强制置 1 | 需要 root、模块签名/安全启动 | 高 |
| 直接写硬件 | `mmap` BAR0 / `resource0` 写 `0x419e84` | 未做；需要 root | **极高**（显示/计算共用 GPU，可能挂死整机） |
| 不写寄存器 | 0317 调试器 suspend / GDB / TSG | 已可用，但不是论文的带内触发 | 低，但语义不同 |

**结论**：普通用户态、不改驱动的前提下，**绕不过去**；所有已知入口最后都汇到
`cmpb $0,0x911(...)`。真正的"绕"只有"让驱动开闸"或"换平台"。

## 3.6 开关层：`pGpu+0x911` 又是什么

### 3.6.1 它不是硬件寄存器，是驱动里的一个字节

- `pGpu` 是内核里指向 **OBJGPU**（GPU 对象）的指针；
- `+0x911` 是这个对象里的一个 `bool` 字段（内核堆内存），**不是 GPU 的物理寄存器**，
  用户态也摸不到；
- 含义：**"是否允许执行调试/寄存器访问类操作"的总开关**（从使用点推断；
  NVIDIA 未公开字段名）。

### 3.6.2 它怎么被设置

初始化代码 `__nvoc_init_dataField_OBJGPU` 里：

```
0x17354  mov $0x2, %esi
0x17359  shr %cl, %rsi          ; 对某个 64 位能力/配置值做位测试
0x1735c  test %rsi, %rsi
0x1735f  je   ...               ; 不满足 -> 走不置位分支
0x17376  movb $0x1, 0x911(%rdi) ; 满足 -> 置 1
0x17b4c  movb $0x0, 0x911(%rdi) ; 另一分支 -> 置 0
```

- 全二进制**只有这两处写 `0x911`**，都在 GPU 对象构造/数据字段初始化里；
- **没有运行期 setter**；
- 初值来自 GPU 初始化时读到的**能力位/注册表配置**（具体键还没定位，`0x17354`
  的位测试就是入口）；
- 它的读点很多（20+ 处，涉及多个调试/reg-op 路径），不是 reg-op 专用，
  更像"全局 debug/reg access 允许"标志。

### 3.6.3 "关闭"到底关闭了什么

```
用户态 ioctl(0x20800122)
  -> 内核 handler
  -> 读 pGpu+0x911
  -> 0：直接返回（NV_OK / 0x56），不执行任何寄存器读写
```

关闭的是：**"用户态让内核替它执行任意寄存器读写"**。
不是"内核不能访问寄存器"——内核驱动自己一直在读写寄存器，否则 GPU 没法工作。
也不是"硬件没有这个能力"——debugger 路径（0317）证明了 trap handler 活着。

### 3.6.4 是不是"内核态永远不可能被访问"

| 说法 | 判断 |
|---|---|
| "内核态不能访问 GPU 寄存器" | ❌ 不对；内核一直在访问 |
| "用户态发起的任意寄存器访问被禁止" | ✅ 在当前驱动 + 当前启动配置下成立 |
| "以后/换配置也不可能打开" | ❌ 不对；`0x911` 是软件标志，初值来自能力位/注册表 |
| "普通用户态能绕过它" | ❌ 不能；只能让驱动自己写 |

### 3.6.5 想打开它，现实中的三条路

1. **让初始化时置 1**：找到 `0x17354` 位测试读的能力位/注册表键；
   如果是模块参数/注册表，可在加载时置 1（仍需 root + 重载驱动 + 专用机器）。
2. **改驱动**：patch gate 检查或强制 `0x911=1`（root、模块签名/安全启动）。
3. **绕过驱动**：BAR0 直写（root，极高风险，不建议在这台机器上做）。

另外，**RM `0301 SMDebugModeEnable` 已实测不能改它**（§40）；`0x83de` 会话路径
也检查同一个 gate。所以没有"用户态开关"。

## 3.7 这是不是"核心问题"

**是，但要分层说。**

### 3.7.1 对"带内触发"来说，它是唯一的根

- 论文 L3 的第一步是"写控制寄存器 → 全局 stall → 正常上下文 trap"；
- sm120 上这条链的**唯一入口**被 `0x911` 关掉；
- 没有它，后面所有"handler 判据/目标/恢复"都无从谈起；
- 所以它是**锁①**，也是"为什么 32 µs 在 sm120 上不可达"的第一因。

### 3.7.2 它可能不只是"触发锁"，而是"总闸"

这是一个**推断，但很有价值**：

- 如果 `0x911=1`，trap 会走**正常内核上下文**（像 sm86），而不是 debugger-suspend 上下文；
- 那么 §4 里"全局读返回 0 / pbuf 快照 / 0318 阻塞"这些现象**可能一起消失**；
- 论文的 payload（读 preempt buffer、写 preempt_idx/block_restore_flag、EXIT）**可能直接工作**；
- 因此开闸不是"只多一个触发"，而是**把整个 trap 语义换回论文那条**。

这条推断的验证方式很明确：在**专用机器**上把 `0x911` 置 1，跑 `run_l3qspin` /
上游 `level 3`，看是否出现"正常上下文 trap + 可读 preempt buffer + 可重放"。
如果成立，四道锁会同时松动；如果不成立，再回到调试 agent。

### 3.7.3 但它不是"唯一核心"

即使开闸，仍然要回答：

- `0x419e84` 在 Blackwell 上是否仍是 trigger（地址/位语义）；
- 多 hwQueue 的选择性 abort（我们的 A/B 只验证了单流单 kernel）；
- 与驱动状态机的配合（paper 的 EXIT + 记账是否在 595 上被接受）。

所以对导师的建议表述是：

> **锁①（`0x911`/reg-op）是"能不能开始"的问题；锁②③④是"开始之后能不能做对"的问题。**
> 它是最值得先讨论的，因为它是唯一一个"改一个开关可能同时解开四道锁"的点；
> 但它需要驱动/机器层面的配合，不是用户态能解决的。

### 3.7.4 一页证据矩阵（本节）

| 命题 | 证据 | 类型 | 置信度 |
|---|---|---|---|
| `0x20800122` 是通用 reg-op 命令 | ioctl/psize/struct/反汇编调用链 | 代码+静态 | 高 |
| `0x419e84` 由用户态描述符传入 | nv-kernel 0 处；libcuda 13 处；cuxtra 2 处 | 静态 | 高 |
| gate 在寄存器访问之前 | `0x2dd122` / `0x21a9cc` 反汇编 | 静态 | 高 |
| gate=0 时无寄存器操作 | 反汇编返回路径 + PTIMER 读 0 + 计数不停 | 静态+动态 | 高 |
| `0x911` 是 init-only 软件标志 | 仅两处写，均在 `__nvoc_init_dataField_OBJGPU` | 静态 | 高（对本版本） |
| 开闸可能恢复论文语义 | 推断：正常上下文 → 全局读/状态机 | 推断 | **中（待专用机验证）** |
| 没有第二条用户态入口 | 已枚举已知路径；RPC 变体未验 | 经验性 | 中 |

## 3.8 5090 实测（2026-10-26，595.71.05）：锁同样关闭，handler/0317 可用

租用了一台 RTX 5090 做对照（`evidence/rtx5090_595_71/`）：

| 项 | 值 |
|---|---|
| GPU | RTX 5090，compute cap **12.0**，32 GB |
| 驱动 | **595.71.05**（与 5060 的 595.99.02 同分支） |
| 工具链 | CUDA **12.8**、g++ 11.4、Ubuntu 22.04 容器 |
| 容器权限 | **无 CAP_SYS_PTRACE**（`!cap_sys_ptrace`，Yama=1） |

### 3.8.1 锁测试：和 5060 一样是关的

| 测试 | 结果 |
|---|---|
| `regops` 读 `PMC_BOOT_0` / `PTIMER_TIME_0/1` | **0 / 0 / 0**，`status=0x3a` |
| `read w/ channel` | **status=0，value=0**（控制成功但 op 被跳过） |
| 写 `0x419e84` bit31 | **status=0x3a**，无副作用 |

⇒ **595/Blackwell 的 `0x911` 策略是共同的，不是 5060 这块卡的问题**。
换 5090 不会打开带内触发。

### 3.8.2 基础能力与 GDB

- sm_120 内核正常：`clockRate=2407000 kHz`，spin 计数正常；
- **cuda-gdb attach/detach 可用**，但容器缺 `CAP_SYS_PTRACE`，目标必须先
  `prctl(PR_SET_PTRACER, PR_SET_PTRACER_ANY)`；否则 `ptrace: Operation not permitted`；
- 3 秒 hold 实测：counter 在 `t=2400` 为 `3,170,429`，`t=2600` 为 `3,178,190`
  （wall +3.08 s），detach 后继续增长并最终 `done` ⇒ **冻结/恢复成立**。

### 3.8.3 活体 handler：布局与 595.99 完全一致

`find_live_handler` + `l3x` 实测：

| 项 | 5090/595.71 | 5060/595.99 |
|---|---|---|
| slot20 `stub` / `hsize` | `0x880` / `0x940` | 同 |
| tools image | `base+0x15f5300`, size `0x1300` | 同 |
| `[0,0xa00)` vs `.text.do_pause` | **0/160 opcode mismatch** | 同 |
| live handler | `base+0x15f0f00`，fingerprint **MATCH** | 同 |
| scratchpad / reason tables | `base+0x1a00000` / `base+0xc38300` | 同 |
| patch `+0x390` 回读 | 16 B 完全一致 | 同 |

⇒ **我们的 live-handler patch 可以移植到 595.71**。

### 3.8.4 0317 与 kill 流程

| 流程 | 结果 |
|---|---|
| `l3x` target/agent，plain context，0317 | 签名 **`0x5aa5/0 reason=0x1`**；victim 12.5 s `cudaSuccess`（内核继续，不 suspend） |
| `L3X_ARM_PATCH` kill 流程，8 s victim | victim 8 s → **3.395 s** `cudaSuccess`，签名 `0/0`（cave 是 GUARD 不是 signature）；agent `devflag arm ack=0xffffffff`，报 **PARKED**，release 后仍 PARKED；后续 compute 对象 session 返回 `0x33` |
| 同上，**20 s victim**（复测） | victim 20 s → **3.426 s** `cudaSuccess`，counter `110,788,608`；同样 `0/0`、`devflag arm=0xffffffff`、PARKED、release 失败 |

**判读**：
1. **0317 陷阱与 live-handler patch 在 5090 上可用**（签名/指纹/回读都对）；
2. **guard 早退是生效的**：victim 无论 8 s 还是 20 s 都在 ~3.4 s 结束，说明不是自然跑完；
   但 5060 的 **0.234 s 干净 kill 没有复现**，5090 上是 **guard 路径 + 3.4 s**，
   不是同一个时序；
3. **0317 的 park 路径不是 kill 路径**：agent 报 `PARKED`、`devflag arm=0xffffffff`、
   release 后仍 PARKED；后续 compute 对象 session `0x33`。要复刻 5060 的 0.234 s，
   需要把 target helper / agent 的 devflag 握手和 guard 时序重新对齐；
4. **pbuf 地址是会话/模式相关的**：同一次 campaign 里，trap 流程报
   `preempt-buf=base−0x6000000`，kill 流程报 `base−0x8000000`（都是 `memobj=1`,
   `size=0x41c54e0`）。这说明不能像 `l3x` 那样只在 handler+0x250 解一次；
   我们的 HAL 在 Init 时从 `do_read+0x120/0x130` 重读的机制是对的，
   移植到 595.71 时要按会话状态重新读。

### 3.8.4b campaign 环境与复现

- 驱动：595.71.05，**GSP 595.71.05**，open kernel module；
- `libcuda.so.595.71.05` 91.5 MB，md5 `b0e0d60418a7f4b4f292233ab4bd86bd`；
  `libcudadebugger.so.595.71.05` 11.7 MB，md5 `cab0518793c73f42a4686cc9597ee3ca`；
- CUDA runtime 13.2，nvcc 12.8.93，cuda-gdb 12.8，Ubuntu 22.04；
- 容器 caps：无 `cap_sys_ptrace` / `cap_sys_module` / `cap_sys_admin`；
- GDB 3 s hold：counter `2,837,032`（t=2200）→ `2,907,447`（t=2400，wall +3.12 s），
  与 5060 的冻结行为一致；
- 所有日志：`evidence/rtx5090_595_71/campaign/`（env、regops、gdb/spin、target/agent trap/kill）。

### 3.8.5 结论

- **5090 不是"解锁卡"**：锁、handler 布局、0317 行为都与 5060 同源；
- **GDB backend 与 trap-handler patch 可移植**（含 0317 签名）；
- **managed kill/park-release 需要按 595.71 重新校准 pbuf 地址**，不是"换卡就好"。

证据：`evidence/rtx5090_595_71/`（`env.txt`、`regops_read/write.log`、`spin*.log`、
`gdb*.log`、`find_live_handler.log`、`target*.log`、`agent*.log`）。

## 4. sm120/595：子命题 B/C 的证据（`0317` 是带外、context 级、调试器上下文）

### 4.1 0317 的身份与前提

- 它是 RM `0x83de0317`（`KernelSMDebuggerSession` 的控制命令），经 GSP 处理，
  需要调试器会话 + `RS_ACCESS_DEBUG`（`0xd04` 共享）——见 `RM_REVERSE_ZH.md` §3；
- 无应答者时**阻塞**（`FINDINGS v2.7`）；cuda-gdb 在场时返回 0（`exp_gdb_cancel1.log`）；
- 它不是"写控制寄存器"，是**调试器 suspend 命令** ⇒ **带外**。

### 4.2 四态实验：同一个 0317，结果由上下文状态决定

| 上下文状态 | 0317 的结果 | 证据 |
|---|---|---|
| 普通 CUDA 上下文（l3x） | benign trap：进 handler（签名 `0x5aa5`、`reason=0x1`），内核继续 | `exp_sig_rm0317.log` |
| 受管 + `InstrMemAllocator`（默认） | **context 级 cancel**（27–30 ms，stream 判完成） | `exp_managed_spin1.log` |
| 受管 + `NO_ICTX_INSTRMEM` | **no-op**（status 0，但不停） | `exp_no_ictx_instrmem.log` |
| CUDA init 前外部 tracer | **park**（计数冻结、`Synchronize` 不返回，0318 不可释放） | `exp_strace_park1.log`、`exp_plaingdb_park1.log` |
| cuda-gdb 应答 | cancel（27.3 ms） | `exp_gdb_cancel1.log` |

**范围**：cancel/park 都是**整个 context**，不是某个 hwQueue ⇒ **B 的 sm120 侧成立**。

### 4.3 目标数据：0317 陷阱里 pbuf 全 0

| 读/写 | 结果 | 证据 |
|---|---|---|
| 0317 陷阱读 `pbuf+0/+4/+8` | **全 0**（可读、不 fault） | `exp_arm_pbuf_{flag0,cmd4,idx8}.log` |
| `R2`（reason） | **0x1**；cmd=2 本应至少得 `0x30 (0x10|0x20)` | `exp_arm_sentinel_host.log` |
| 设备 writer 自己的 launch trap | `0x8` | `exp_arm_sentinel_dev.log` |
| 陷阱内对 `pbuf+4` 发 `ST.E` | 不 fault，但写 1/写 2 行为相同 ⇒ 不与驱动共享 | `exp_arm_pbuf_write_r2.log`、`exp_arm_pbuf_write2.log` |

⇒ 0317 没有 `preempt_idx/kernel_idx` 数据，**没有 B 里的"按 queue 目标选择"**；
reason 只是 SR 的通用位，不是 XSched 的专用中断标识。

### 4.4 为什么说它是"debugger-suspend 上下文"（C）

| 观测 | 正常内核上下文（sm86） | sm120 的 0317 陷阱 | 证据 |
|---|---|---|---|
| 读自己的全局 buffer | ✅ | **0** | §35、`exp_const_probe*.log` |
| 读 XSched preempt buffer | ✅ | **0** | §35 |
| 读 host-mapped UVA | ✅ | **0** | §35 |
| 读代码页 / 描述符 LDG | ✅/不适用 | **700** | §35 |
| 驱动 pbuf | 不适用（不是这条路径） | 可读但全 0；store 不共享（快照/私有映射） | §52 |
| launch trap | — | `reason=0x8`；读重定位 pbuf 会 700 | §41、§52 |
| 0317 trap | — | `reason=0x1` | §52 |
| 恢复 | handler 写 `block_restore_flag`，host 重放幂等 kernel | 0318 在无调试器时阻塞；裸 `EXIT` 破坏重放（final 700） | §29/§30、`exp_reason_arm_exit.log` |
| 延迟 | 32 µs (GV100) / 229 µs (3090) | 27–30 ms cancel / 116 ms GDB | §50、`report/01` §5 |

这张表是 C 的核心：**同一个 handler payload 在 sm86 上能读 `global_exit_flag`，
在 sm120 的 0317 陷阱里读到 0**。所以不是 payload 写错了，是它运行的**上下文**变了。

## 5. 反证与替代解释（为什么不是别的原因）

| 替代解释 | 反证 | 结论 |
|---|---|---|
| "handler 没执行 / patch 错了" | 签名 `0x5aa5`、`reason=0x1`、sentinel 记录页写入、cave 在 `+0x390` 被 CALL | 排除 |
| "带内触发只是没找到" | 接口存在（`0x20800122`/`cuXtraTriggerTrap`），静态定位到闸门，动态 status 0 无副作用；A/B 同码 sm86 可用 | 不是"没找到"，是"被关" |

## 7. 什么实验会推翻这个判断（可证伪性）

1. 在 sm120 上找到一条**运行期**写 `pGpu+0x911` 的路径并成功写 `0x419e84`，
   使内核出现**与 0317 不同**的 reason，且 handler 能读到 host 写的 flag/target
   ⇒ "入口被关"不成立（或至少不是唯一入口）。
2. 在 0317 陷阱里读到 `pbuf+4=2`、`+8=kernel_idx`，且写 2 能触发 `preempt_save`
   ⇒ "0317 没有 request/target"不成立。
3. 在 sm120 上把 context 切到某种状态后，陷阱里全局读返回非 0
   ⇒ "debugger-suspend 上下文读 0"只对当前状态成立，需要重新定义 C。
4. 换驱动版本（如 570/580/595 的另一 build）后 `0x911` 出现运行期写入点
   ⇒ 结论变成版本相关，而不是平台相关。

|---|---|---|
| 触发 | ioctl 写 GPU 控制寄存器（`0x419e84`） | RM `0x83de0317` 调试器 suspend |
| 调试器会话 | 不需要 | 需要（`0x83de` + 应答/`cuda-gdb`） |
| stall 范围 | 全局 stall（论文原文） | context 级 cancel/park/no-op |
| 目标选择 | `preempt_idx == kernel_idx`（hwQueue 记账） | pbuf 全 0，无 target |
| trap 上下文 | 正常内核上下文，全局读写可用 | debugger-suspend，全局读 0 |
| 恢复 | handler 记账 + host 重放幂等 kernel | 0318 阻塞 / 裸 EXIT 700；GDB 116 ms |
| 延迟 | 32 µs (GV100) / 229 µs (3090) | 27–30 ms / 116 ms |

**三句话**：
1. "论文的 L3 是**带内写控制寄存器**，trap 进**正常上下文**，handler 靠 **preempt buffer
   的 flag + preempt_idx** 选目标；我们在 3090 上用同一套代码复现到 229 µs。"
2. "sm120/595 的这条入口被 `pGpu+0x911` 在启动期关了；我们唯一能触发的是
   **RM 0317 调试器 suspend**，它是**带外、context 级**，pbuf 里**没有 request/target**。"
3. "所以差别不是 handler 会不会执行，而是**入口和它带来的目标/恢复所有权**；
   要补只能做进程内调试 agent，或者换平台。"
