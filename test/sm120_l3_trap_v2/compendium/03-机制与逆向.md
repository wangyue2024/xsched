## 3. cave 的硬约束（血泪教训）

1. **R1 绝对不能用**：handler 在 `+0x3a0` 紧接 cave 返回后执行 `STL.64 [R1], R2`，
   覆盖 R1 → 非法局部地址 → 700。
2. 可自由用 **R4–R11**；R0–R3、R12 谨慎。
3. 返回前 `IADD R12, R12, 0x10`，再 `RET.ABS R12`（恢复 0x20 偏移）。
4. `R2` 是 reason，**不要清零**（否则 handler 会重执行 fault 指令）。
5. 指令写：Init 时 host 可写（`cuXtraMemcpyHtoD`）；运行期改用设备侧 writer
   （`l3write` PTX，1 block × 1 thread，从 `wr_buf` 拷 4 字节）。

## 5. 驱动 preemption buffer 协议（handler 的真正输入）

handler 的 `do_read_trap_reason` 通过 **`LD.E.CONSTANT`** 读 `base-0x2000000`：

| 偏移 | 含义 | 值 |
|---|---|---|
| +0 | exit flag | 非 0 = 退出 |
| +4 | command word | **2** = preempt_save + do_pause；**1** = preempt_restore |
| +8 | preempt_idx | 当前抢占的 warp/上下文索引 |

- 该地址是驱动在 GPU attach 时 patch 进 handler 立即数的（`do_read+0x120/0x130`）。
- 驱动还会 patch scratchpad 地址（`do_read+0x90/0xa0` 等），同样是立即数。
- 该 buffer 在**设备/trap 地址空间**：trap 可 `.CONSTANT` 读，`ST` 即 700；
  用户进程 VA 里是 PROT_NONE 匿名占位（CPU 读到零页）；设备 kernel store 非法。
- 写它的只有驱动/调试 agent（`libcudadebugger` 的 `IPreemptionBufferAccessor`）。

**这解释了所有现象**：XSched 的 `Deactivate()` 写自己的 preempt buffer，handler 根本不看；
在我们的稳定配置里 reason 是 `0x1`（SR 位；唯一例外是 §18 的一次 post-resume `0x8`），
命令字位 `0x10/0x20` 永不出现。

## 6. scratchpad 布局（per-warp 记录）

从 `do_read_trap_reason` / `do_pause` 的 SASS：

```
R0 = warp/SM 索引;  R0 *= 0x2a0;  R4 = scratch_base + R0
do_read:  LD.E.U8.CONSTANT R0, [R4+0x29d]
do_pause: ST.E... [R4+0x290] / [R4+0x294] / [R4+0x298] / [R4+0x29e]
```

- 每条 warp 记录 **0x2a0 字节**；驱动只用 `+0x290..+0x29e` 附近几个字。
- host 侧是 `rw-s /dev/nvidiactl` 映射（唯一 CPU 可写的 trap 相关区域）。
- trap 可见范围只覆盖**当前活动的 per-warp 记录**：盲读 `+0x270/+0x300/+0x1000`
  在 launch trap 就 700（即使不写 host）；写这些位置还会破坏 CILP 现场。
- `+0x29d` 是 defer-continuation 状态，不是请求/应答字段。

## 7. trap 上下文的内存语义（汇总）

| 操作 | 结果 |
|---|---|
| 读普通全局内存（设备内存 / XSched buffer / host-mapped UVA） | **恒 0** |
| 读代码页（`live+0x390`） | 700 |
| 读带描述符的 `LDG.E` | 700 |
| 读常量库 `c[0x170..]` | ✅ |
| 读 SR（`SR_GLOBALERRORSTATUS` 等） | ✅ |
| 读驱动 pbuf（`.CONSTANT`） | ✅（设备侧只读） |
| 读 scratchpad（活动 per-warp 记录内） | ✅ |
| 写普通全局内存 | ✅（host 回读一致） |
| 写 scratchpad | ✅（驱动布局内） |
| 写驱动 pbuf | ❌ 700 |
| 写代码页 | 需 `cuXtraInstrMemcpyHtoD`/设备 writer（运行期 host 写会阻塞） |

## 8. RM / 0x83de 速查

**ioctl**：`NV_ESC_RM_ALLOC=0xc030462b`、`NV_ESC_RM_CONTROL=0xc020462a`、
`NV_ESC_RM_FREE=0xc0104609`、`NV_ESC_RM_DUP=0xc01c4634`、`NV_ESC_RM_SHARE=0xc0184635`。

**结构**：`NVOS21`(48B)、`NVOS54`(32B)、`NVOS00`(16B)、`NVOS55`(28B)。

**0x83de（KernelSMDebuggerSession）常用命令**（完整表见 `../RM_REVERSE_ZH.md §3`）：

| cmd | 名称 | clrSize | 状态 |
|---|---|---|---|
| 0301 | SMDebugModeEnable | 0 | 接受，不改变 park/cancel |
| 0302 | SMDebugModeDisable | 0 | 未测 |
| 0307 | DebugSetModeMMUDebug | 4 | 接受 |
| 0309 | DebugSetExceptionMask | 4 | 接受 |
| 030c | DebugReadAllSmErrorStates | 0x12d8 | 只读控制 |
| 0313/0314 | 单步/中断处理 | 4 | 未改语义 |
| **0315/0316** | **DebugRead/WriteMemory** | 0x18 | 仅 RM memobj，有边界检查 |
| **0317** | **DebugSuspendContext** | 8 | 阻塞 / 0xffff / 0 |
| **0318** | **DebugResumeContext** | 0 | 所有 client 阻塞 |
| 031d | DebugExecRegOps | 0xc88 | 被 `pGpu+0x911` 挡 |
| 031f/032a | 错误栏/MMU GCC 调试 | 4 | 接受 |
| 0321–0324 | 单 SM 单步/触发/运行/跳过空闲检测 | 8 | 未改语义 |
| 0329 | DropDeferredRC | 1 | 未测 |

**0315/0316 参数**（`_nv83deCtrlCmdDebugAccessMemory@0x21a000`）：

```c
struct { uint32_t hMemory; uint32_t size; uint64_t offset; uint64_t hostbuf; }; // 0x18
// offset + size <= memdesc.size 才放行；只能访问 RM Memory 对象
```

**权限**：跨 client 建会话需 `RS_ACCESS_DEBUG`；`os_check_access()` 对 DEBUG 永远
返回 FALSE，只能靠 target 发 `0xd04` share policy。会话构造要求
`hDebuggerClient_deprecated == 0`、`hAppClient` 合法、`hClass3dObject` 是 0xcec0；
构造后 `kgrctxRegisterKernelSMDebuggerSession` 把会话挂到 `kgrctx+0x680` 链表。

## 10. cuXtraTriggerTrap 的真实实现

从 `3rdparty/cuxtra/lib/libcuxtra_linux_x86_64.a`（`trap.cpp.o` / `kmod.cpp.o`）：

```
cuXtraTriggerTrap(ctx)
  -> CudaKernelModule::GetKMod(ctx)
  -> GlobalRegsWrite32(vector<DriverWrite32Params>)
       ioctl(NV_ESC_RM_CONTROL=0xc020462a)
       cmd = 0x20800122 (GPU_EXEC_REG_OPS), paramsSize = 0x30
       ops: {reg=0x419e84, value=0x80000000, mask=0x80000000}   # bit31 set
            {reg=0x419e84, value=0x00000000, mask=0x80000000}   # bit31 clear
       // 第三个字段按 RegOp32 布局推断为 mask；前两个字段（reg/value）来自
       // GlobalRegsWrite32 的拷贝逻辑（reg@+0xc, value@+0x14, 第三字段@+0x1c）
```

**⇒ 我们的探针写得没错；问题在 `pGpu+0x911` 早退（函数开头 `cmpb $0,0x911(%gpu)`）。**
该能力位全二进制只有两处写，都在 `__nvoc_init_dataField_OBJGPU`（GPU init），
运行期无写点。

## 12. 上游 sm86 的 L3 实现（A/B 参考，2026-10-26）

上游 `XpuOS/xsched`（commit `f49289f`）在 `platforms/cuda` 里给出了论文的 NVIDIA L3 实现：

```
CudaQueueLv3Trap (sm70/sm86，arch.cpp)
  └─ Suspend()
       └─ InterruptContext::Interrupt()
            └─ cuXtraTriggerTrap(kCtx)
                 └─ CudaKernelModule::GlobalRegsWrite32
                      ioctl(NV_ESC_RM_CONTROL, cmd=0x20800122)
                      ops: 0x419e84 <- 0x80000000 (bit31 set)
                           0x419e84 <- 0x00000000 (bit31 clear)
  └─ 首次 launch 前：InterruptContext::InstrumentTrapHandler()
       ├─ cuXtraGetTrapHandlerInfo(ctx, &dev, &size)
       ├─ cuXtraMemcpyDtoH(host, dev, size)
       ├─ TarpHandlerSM86::Instrument(host, dev, size, inject_host, inject_dev)
       │    （改写 handler 的 trap-inject 点 + 写入 guardian/resume 指令）
       ├─ cuXtraInstrMemcpyHtoD(inject_dev, ...)
       ├─ cuXtraMemcpyHtoD(dev, host, size)
       └─ cuXtraInvalInstrCache(ctx)
```

**实测（RTX 3090，sm86，570.124.04）**
- `level 3`：preempt p50 ≈ **229 µs**、p99 ≈ 310–2233 µs、restore ≈ 90 µs；
  dead-loop 内核可停可恢复。
- `level 1`：p50 ≈ 12.5–13.2 ms（等内核完成）。

**和 sm120 的差别**
- sm86/570：`0x20800122` 真执行（还能读 `0x200510`/`0x419e84`），cuxtra 触发 + SM86
  插桩 handler 工作。
- sm120/595：`0x20800122` 被 `pGpu+0x911` 早退（返回 0、无效果），`cuXtraTriggerTrap`
  无法投递；只能 RM 0317（27 ms）/ GDB（116 ms）。
- **只写寄存器不插桩 handler 不够**：A100 上我们只做 regops 写，内核照跑；
  必须用 `TarpHandlerSM86::Instrument` 改写 handler，触发才会 abort 内核。

证据：`../FINDINGS_ZH.md §49`、`../evidence/ab_ampere/logs/`。
