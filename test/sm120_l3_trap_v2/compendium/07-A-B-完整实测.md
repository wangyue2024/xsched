# 07 A/B 完整实测（2026-10-26）

> 两台租用机 + 上游 `XpuOS/xsched` 原样复现论文 L3；本文汇总所有批量测试、正确性、
> handler 逆向、调试器路径对照和失败模式。证据在 `../evidence/ab_ampere/`。

---

## 1. 机器与软件

| 机器 | GPU | 驱动 | 架构 | GSP | 容器能力 |
|---|---|---|---|---|---|
| 本地 | RTX 5060 | 595.99.02（开源模块） | sm120 | on | 有显示，可 root |
| A100 | A100-PCIE-40GB | 550.107.02（专有模块） | sm80 | on | 无 `cap_sys_module/admin/ptrace`，驱动固定 |
| 3090 | RTX 3090 | 570.124.04（开源模块） | sm86 | on | 无 `cap_sys_module/admin/ptrace`，驱动固定 |

上游代码：`XpuOS/xsched` main，commit `f49289f`（2026-08-19）。
构建：CUDA 12.1 + g++11 + CMake 3.22（3090）；A100 同版本；`-arch=sm_86` 或 `sm_80`。
需补 `3rdparty/cuxtra`（与上游子模块 `XpuOS/cuxtra` 的库 **md5 相同**）和
`3rdparty/ipc`（include/src/tools + boost-ipc），CMake 3.22 下临时关 ipc 的
`if (BUILD_TEST)`。

## 2. 3090（sm86/570）批量结果

同一 `output/bin/cuda/level`，`LD_LIBRARY_PATH=output/lib`（含 shim 软链）：

| 配置 | 2000 µs block 的 p50 | dead-loop p50 | dead-loop p99 | restore avg |
|---|---|---|---|---|
| level 1 | 13.38 ms | — | — | 8.2 µs |
| level 2 | **1.257 ms** | — | — | 57.3 µs |
| level 3 run1 | 231.4 µs | **241.1 µs** | 452.0 µs | 127.1 µs |
| level 3 run2 | 230.5 µs | **230.8 µs** | 2825.5 µs | 93.3 µs |
| level 3 run3 | 227.3 µs | **235.2 µs** | 420.3 µs | 119.7 µs |
| level 3 TSG | 13.35 ms | 超时（180 s） | — | 276.8 µs |

- 三次 L3 p50 非常稳定（230–241 µs），restore 93–127 µs；p99 有偶发长尾（0.42–2.8 ms）。
- TSG 路径明显慢（~13 ms），且 180 s 内没跑完 dead-loop；只保留已完成的 block 数据。

**去掉 shim 的对照**（把 `output/lib/libcuda.so*` 软链改名，直接跑 HAL）：

| block time | p50 | restore |
|---|---|---|
| 10 µs | 7.2 ms | — |
| 60 µs | 9.7 ms | — |
| 500 µs | **34.0 ms** | 26.5 ms |

⇒ **快路径依赖 shim 的 managed launch**（`XLaunchKernel` → `CudaKernelCommand` →
debugger params/guardian）；只装 handler + 触发不够。

## 3. 正确性（3090，sm86）

`probe/correct_ab.cu`：16M 个 int 的 `C=A+B`，在 400 次 kernel launch 期间做
**200 次 `XQueueSuspend/Resume`**，最后逐元素校验：

```
[done] cycles=200 stream=no error
[verify] bad=0 / 16777216 -> OK
```

- 前 5 次 `Suspend` 226–442 µs（含 `XQueueSuspend` 全流程）；我们测得 resume ~5.1 ms
  是因为测试自己在 resume 前 `usleep(5000)`，不是纯 restore。
- 200 次抢占后结果 bit-exact，说明 sm86 的 L2/L3 restart 语义对 idempotent 内核正确。

## 4. trap handler 实物

`cuXtraGetTrapHandlerInfo` + `cuXtraMemcpyDtoH`：

| 机器 | handler 地址 | size | +0x3e0 words |
|---|---|---|---|
| 3090 sm86 | 0x7fde6d219900 | **0x1200** | `fffffff001017810 004fe40007ffe0ff` |
| A100 sm80 | 0x7fec4f20f400 | **0x1200** | `fffffff001017810 004fe40007ffe0ff` |

- 上游 `TarpHandlerSM86::Instrument` 把 **handler+0x3e0**（`IADD3 R1,R1,-0x10,RZ`）
  替换为 `JMP inject_dev`，注入 `trap_inject_instrs` + 原指令 + 跳回；注入大小
  `sizeof(trap_inject_instrs) + 2*16`。
- sm86 与 sm80 的 handler 大小、+0x3e0 指令**完全一致**；但 sm86 的注入 SASS 在 sm80 上
  仍不能直接用（见 §6）。
- 二进制：`../evidence/ab_ampere/sm86_handler.bin`、`a100_handler.bin`。

## 5. cuda-gdb 调试器路径（跨架构）

| 机器 | attach | detach | ioctl 序列（目标进程） |
|---|---|---|---|
| 3090/570 | 0.047 s | 0.045 s | `0307 → 0317{1,0} → 0315/030c/0316 → 0318` |
| A100/550 | 0.159 s | 0.267 s | 同 0317 序列 |

⇒ cuda-gdb 在所有架构上走的都是 **debugger-suspend**（0317/0318），不是 cuxtra 的带内
寄存器触发；两条路径独立。证据：`sm86_agent_ioctl_0317.log`、`a100_agent_ioctl_0317.log`。

## 6. A100（sm80/550）为什么不能直接复现

| 实验 | 结果 |
|---|---|
| `0x20800122` 读 PTIMER/0x419e84 | ✅ 可读（0x3313/0x1c01）；写 bit31 返回 0，回读不变，内核不停（未插桩 handler） |
| 上游 `level 3`（带 shim） | ❌ SIGSEGV in **`cuXtraKernelGetFunction`** ← `CudaKernelCommand` ← `XLaunchKernel`（libcuda 550） |
| 上游 `level 3`（无 shim） | ⚠️ 能跑但很慢：300 µs block p50 **33.6 ms**、400 µs p50 **46.4 ms**、restore 25.8 ms；180 s 超时 |
| TSG 路径（无 shim） | ⚠️ 10–40 µs block p50 0.58–1.49 ms；900 µs 时 p50 **55.7 ms**；超时 |
| sm80→SM86 arch 补丁（带 shim） | ❌ 同一个 `cuXtraKernelGetFunction` segfault；**不能据此判断注入 SASS 是否兼容** |
| cuxtra 库版本 | 上游子模块与本地库 **md5 相同**；崩溃是 550 驱动/cuxtra 兼容问题，不是拿错版本 |

- A100 的快路径被 **cuxtra ↔ 550** 卡住；没有 shim 时，HAL 的 trap/TSG 都是驱动级慢路径
  （~30–55 ms），与 sm120 的 27 ms 同量级。
- 上游 `arch.cpp` 只支持 sm70/sm86；sm80 需要真正的 SM80 handler/工具链移植，不是改两行
  `case` 就行。

## 7. 根因地图（最终）

```
论文快路径 = managed launch（shim：debugger params/guardian）
           + instrumented trap handler（TarpHandlerSMxx::Instrument）
           + 带内触发（cuXtraTriggerTrap / 0x419e84 bit31 via 0x20800122）
```

| 平台 | managed launch | handler 插桩 | 触发 | 结果 |
|---|---|---|---|---|
| **3090 sm86/570** | ✅ shim | ✅ TarpHandlerSM86 | ✅ regops 开放 | **快路径 229 µs，正确性 OK** |
| 3090 无 shim | ❌ | ✅ | ✅ | 慢 6–40 ms |
| A100 sm80/550 带 shim | ⚠️ cuXtraKernelGetFunction 崩 | — | ✅ regops 开放 | 不可用 |
| A100 sm80/550 无 shim | ❌ | ✅（SM86 插桩） | ✅ | 慢 30–55 ms |
| **sm120 sm120/595** | ✅ shim（XSched port） | ✅ 自研 cave | ❌ `pGpu+0x911` 关闭 | 0317 27 ms / GDB 116 ms |

**结论**：论文 L3 **在 3090（sm86/570）上完整复现**；A100 受 cuxtra/550 兼容性限制，
只能跑慢路径；sm120 受触发闸门限制。差别不在"Ampere vs Blackwell"这一句，而在
**触发入口 + managed launch 工具链**。

## 8. 值得借鉴 / 经验

1. **L3 是三段耦合**：managed launch、handler 插桩、触发。只测触发（regops）或只插桩
   handler 都会得出错误结论；必须三条同时验证。
2. **先做"效果判别"**：用 regops 读寄存器/写 bit31 快速判断闸门是否打开；不要在没有
   效果判别的情况下深挖 handler。
3. **架构/工具链矩阵**：上游只支持 sm70/sm86；cuxtra 与 550 不兼容。换机器前先确认
   架构支持与工具链兼容性，否则会把工具问题误判成硬件问题。
4. **论文数字要按平台看**：32 µs 是 GV100；sm86 实测 229 µs；sm120 的 27 ms/116 ms 是
   调试器路径。跨架构比较没有意义。
5. **快路径依赖 managed launch**：3090 去掉 shim 从 229 µs 退化到 6–40 ms；这解释了为什么
   "只装 handler + 触发"不够，也解释了 sm120 上即使有 cave/payload 也快不起来。
6. **sm120 的可行路线**：打开 `pGpu+0x911`（驱动/注册表，超安全边界）或进程内调试 agent；
   不要继续找 RM mailbox。
7. **可复用的设计**：handler+0x3e0 的"原指令替换 + 注入检查/abort + 跳回"模式、注入缓冲
   大小/跳转编码、shim 的 debugger params 布局，都可以作为 sm120 端口的参考；但 sm120
   的 patch 点（+0x390）和 SASS 编码不同，需要单独移植。

## 9. 局限

- 容器无 `cap_sys_module`/`cap_sys_admin`：不能装 595、不能关 GSP、不能 rmmod；
  530/550/570 与 595 的差异无法在同一张卡上做严格同驱动对照。
- A100 的 cuxtra/550 崩溃阻止了"sm80 快路径"的验证；需要换 cuxtra 实现或真正的 SM80
  端口。
- 3090 的 TSG dead-loop 在 180 s 内未跑完；只保留已完成的 block 数据。
- 所有测试使用上游 `level.cu`（默认 TRAP）；不同 block time 的结果已按日志记录。
