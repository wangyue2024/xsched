# 06 结论与下一步

---

## 1. 需求审计（对照最初目标）

| # | 要求 | 状态 | 说明 |
|---|---|---|---|
| 1 | 中断运行中的内核 | ✅ | GDB backend 完整可用；trap backend 可 cancel（27–30 ms）/ kill（0.234 s）/**park**（外部 tracer + 0317） |
| 2 | 中断后可恢复（同一 context） | ⚠️ | 只有 GDB backend（attach/detach）能恢复；trap 路线的 park 无用户态释放手段（0318 全 client 阻塞） |
| 3 | 不破坏在飞工作 / 结果正确 | ⚠️ | GDB 冻结路径结果 bit-exact（v0.6）；kill+replay 正确完成（done=1）；park 不丢工作但不可释放；cancel 依赖重放 |
| 4 | 不依赖 cuda-gdb | ⚠️ | **停**已可摆脱 cuda-gdb（plain tracer + 0317）；**恢复**仍需调试 agent（libcudadebugger） |
| 5 | 接入 XSched | ✅ | GDB backend 进 HAL + `l3ctl`；trap backend 进 HAL（探针/回放/会话管理） |

**一句话**：功能上"能停能恢复"的形态是 GDB backend；"trap 原生 + 可恢复"在纯用户态
不可达，缺的是**可区分的带内中断源**和**命令字写权限**。

## 2. 延迟账本

| 场景 | 数字 | 口径 |
|---|---|---|
| 论文 GV100 Lv1 | ~4 ms（8T） | OSDI'25 §6.3/§7.3 |
| 论文 GV100 Lv2 | ~0.5 ms（1T） | 同上 |
| **论文 GV100 Lv3 P99** | **32 µs** | handler 内 abort + 从头重启 |
| 我们：GDB 设备静止 | **116 ms** | attach 后 CILP save 的物理时间（5 ms 采样） |
| 我们：GDB 真实 attach | **~23 ms** | `Prepare` 预热后；未预热另有 ~0.3 s gdb 启动 |
| 我们：GDB `Suspend()` 返回 | 0.52–0.54 s | **测试脚本口径**，其中含脚本自身 0.5 s sleep |
| 我们：GDB 租户完成 | 0.73–0.74 s | 同一脚本口径；三轮抖动 < 3 ms，`Resume=1` |
| 我们：trap 设备真正停住 | **0.204 ms** | 预建会话 + eager，50 µs 阈值（§33） |
| 我们：trap `Suspend` 返回 | **22.9 ms** | 停住之后的驱动 cancel/teardown |
| 我们：trap cancel | 27–30 ms | 受管上下文默认 |
| 我们：kill（standalone） | 8 s → **0.234 s** | 结果正确 |
| 我们：首次触发额外 | 4.72 ms | 会话创建 + shm 轮询 |
| **我们：sm86/570 上游 L3（level 3）** | **p50 227–229 µs；p99 310–2233 µs** | RTX 3090，含完整 suspend |
| 我们：sm86/570 restore | 38–97 µs | 同一测试 |
| 我们：sm86/570 level 1 | 12.5–13.2 ms | 无 L3，等 kernel 完成 |

**结论**：0.204 ms 证明"停住"本身不慢；22.9 ms / 116 ms 都是**收尾/驱动状态机**的成本。
**sm86/570 的 229 µs 证明：只要触发可用，handler-abort 机制在 Ampere 上成立**；
sm120 的 27 ms / 116 ms 是触发不可用后的替代路径。

## 3. 路径决策

| 路径 | 能力 | 代价 | 建议 |
|---|---|---|---|
| GDB backend | park + resume，结果正确 | cuda-gdb，116 ms 设备静止 | **交付/生产** |
| trap kill + replay | 停/杀 + 重放 | 无原地恢复；cancel 收尾 20+ ms | 适合 idempotent 内核的快速抢占 |
| trap park-only | 真 park，亚毫秒级停 | 不可恢复 | 仅适合"停住后不恢复"（驱逐/销毁） |
| 论文式 handler abort | 32 µs 级 | 缺带内中断源 + 判据 | **sm86/570 ✅（p50 229 µs）；sm120 ❌** |
| 调试 agent（libcudadebugger） | park + resume，无需 gdb 进程 | 工程量大（协议/注入/映射） | **唯一能补全 sm120 trap-native 的方向** |
| 换平台（Ampere/V100 + 可控 GSP/驱动） | 可能复现论文 | 硬件/环境成本 | **已在 sm86/570 验证（level 3 跑通）** |

## 4. 与论文的最终对照

| 维度 | 论文（GV100） | sm86/570 实测（2026-10-26） | 我们（sm120/595） |
|---|---|---|---|
| 停住入口 | ioctl 写 GPU 控制寄存器 | 同路径：`cuXtraTriggerTrap`（`0x419e84` bit31） | RM 0317（debugger-suspend） |
| handler | 插桩 | `TarpHandlerSM86::Instrument` | 自研 cave/payload |
| 判据 | trap reason | 插桩 handler 的 trap-inject | 稳定配置 reason 0x1（例外 §18） |
| abort | handler 内 exit | **工作**（level 3） | payload EXIT 可杀，但无判据区分 launch |
| 恢复 | idempotent 重跑 | 同（restore ≈ 90 µs） | 同，但需调试 agent restore/teardown |
| 状态机归属 | XSched | XSched | GSP + libcudadebugger |
| 延迟 | 32 µs | **p50 229 µs / p99 310–2233 µs** | 0.204 ms 停 / 22.9 ms 收尾 / 116 ms GDB |

**根因排序**：① sm120/595 的 `pGpu+0x911` 关闭了 regops/带内触发（sm86/570 打开）；
② 触发不可用后，只能用 debugger-suspend，其命令字又只能由调试 agent 写；
③ trap 数据读通路不通，使软件判据也不可行。三者叠加，导致 sm120 的"停/恢复"必须借用调试器。

## 5. Ampere A/B 实测（2026-10-26）

**已执行**：RTX 3090（sm86，570.124.04，GSP on，容器）+ 上游 `XpuOS/xsched`
（commit `f49289f`）。

| 项 | 结果 |
|---|---|
| 构建 | CUDA 12.1 + g++11 + CMake 3.22；补 `3rdparty/cuxtra`、`3rdparty/ipc`（boost-ipc/tools）；`-arch=sm_86` |
| `level 3` | preempt p50 **227–229 µs**、p99 310–2233 µs、restore 38–97 µs；dead-loop 可停可恢复 |
| `level 1` | p50 12.5–13.2 ms（等 kernel 完成），restore 7 µs |
| 路径 | `CudaQueueLv3Trap` → `InterruptContext::InstrumentTrapHandler`（`TarpHandlerSM86::Instrument`）→ `cuXtraTriggerTrap`（`0x419e84` bit31） |
| A100（sm80/550） | regops 开放（可读 `0x200510`/`0x419e84`，写 bit31 返回 0），但 sm80 不在上游 TarpHandler 支持列表；只写寄存器不插桩 handler → 内核照跑；cuda-gdb 仍走 0317/0318 |
| sm120/595 | `0x20800122` 被 `pGpu+0x911` 早退；`cuXtraTriggerTrap` 无法投递；只能 0317（27 ms）/ GDB（116 ms） |

**结论**
- 论文的 L3 方法在 **sm86/570 可复现**（p50 229 µs，远好于 sm120 的 27 ms/116 ms）。
- sm120/595 的差别是 **regops 能力位被关**，不是 handler 机制本身；
  A100 的"写寄存器不停"是因为 sm80 不支持 + 没插桩 handler，不是反例。
- **未能验证**：595 驱动装到 Ampere、GSP on/off 的控制组（容器无 `cap_sys_module`，
  驱动 550/570 固定）。若需严格同驱动对照，需要能装 595/改模块参数的机器。

**补充 battery（同日；完整版见 `07-A-B-完整实测.md`）**

| 配置 | p50 | 说明 |
|---|---|---|
| 3090 level 2 | 1.257 ms | Lv2 flushing，restore 57 µs |
| 3090 level 3 ×3 | 230–241 µs | p99 0.42–2.8 ms；restore 93–127 µs |
| 3090 level 3 TSG | 13.35 ms | dead-loop 180 s 超时 |
| 3090 level 3 **去 shim** | 6–40 ms | 500 µs block 34.0 ms；快路径依赖 managed launch |
| 3090 正确性 | — | 200 次抢占后 16M 元素 `bad=0 -> OK` |
| A100 level 3 带 shim | — | SIGSEGV in `cuXtraKernelGetFunction`（550） |
| A100 level 3 无 shim | 33.6–46.4 ms | 驱动级慢路径；TSG 0.58–55.7 ms |
| A100 sm80→SM86 补丁 | — | 同一个 cuxtra 崩溃；不能证明 SASS 兼容 |

**三段耦合（最终结论）**
```
managed launch（shim/debugger params） + instrumented handler（+0x3e0） + 触发（0x20800122）
  3090: ✅ + ✅ + ✅ -> 229 µs，正确性 OK
  3090: ❌ + ✅ + ✅ -> 6–40 ms
  A100: ⚠️ + ✅ + ✅ -> 带 shim 崩 / 无 shim 30–55 ms
  sm120: ✅ + ✅ + ❌ -> 0317 27 ms / GDB 116 ms
```
⇒ 论文快路径需要三段同时成立；sm120 的缺口是触发（`pGpu+0x911`），A100 的缺口是
cuxtra/550 兼容性，3090 是唯一三段齐全的实测平台。

**补充（2026-10-26）**：sm120 的 cave 已实测能读 `c[0x180]=kernel_idx`、
`c[0x188]=killable`（`exp_dbgparam_*.log`），所以"my kernel_idx"不再是缺口。
剩余的是 per-suspend 的 **target id** 和 **request/reason**：target 不属于
launch-time debugger params，自然的 preempt buffer 通道数据读回 0；reason 仍是 `0x1`。

**证据**：`evidence/ab_ampere/`（含 `battery_3090/`、`correct_sm86.log`、
`sm86_handler*.bin/log`、`level3_*noshim*.log`、`*_agent_ioctl_0317.log`）、
`FINDINGS §49–§50`。

## 6. 不要再试的清单（已证否）

1. 用 `0x419e84` / `cuXtraTriggerTrap` 在 **sm120** 上触发（regops 被 `pGpu+0x911`
   早退；**sm86/570 上可以**，见 §5）。
2. 扫 `0x83de` 的 0313/0314/0321–0324/0329 等命令来找 park 开关（0301/0307/0309/031f/032a
   已试，无改变）。
3. 用 0315/0316 写 pbuf（只支持 RM memobj，且有边界检查）。
4. 从任何 client 发 0318 释放 park（全阻塞）。
5. 运行期用 cuXtra/CUDA 异步写 pbuf（invalid / SIGSEGV）。
6. 设备 kernel store 到 pbuf（Illegal Address）。
7. trap 上下文 `ST.E` 写 pbuf（700）。
8. `mprotect` pbuf 后 CPU 写（COW 零页）。
9. 盲读/盲写 scratchpad（launch trap 700）。
10. Init 之后才 ptrace attach（不产生 park；必须在 CUDA init 前）。
11. PTRACE_DETACH 释放 park（ESRCH / 无效）。
12. 用 cuda-gdb 写 CUDA PC 来杀 block（被拒）。
13. 把 `cudbgApiInit(2)` 当开关（是注入/attach 框架）。

## 7. 风险与边界

- **不要盲写 GPU 寄存器/BAR0**：未知寄存器可能挂死 GPU/显示；本机显示与计算共用。
- **不要 rmmod/重载驱动**：会中断显示和所有 CUDA 进程；需要用户明确授权。
- **驱动版本敏感**：所有偏移/指纹只对 595.99.02 有效；换版本先跑指纹校验。
- **证据优先**：任何"成功"都要 host 回读、计数器冻结、stream 完成状态三者独立验证。
- **会话副作用**：0x83de 会话存在会改变 launch/代码写行为；用完要释放。

## 8.5 2026-10-26 补测：驱动 pbuf 路线关闭（FINDINGS §52）

在"驱动 pbuf 的 cmd/preempt_idx"这条最后的 mailbox 候选上做了可控实测：

- 载荷在 Init 构建、`Arm()` 在 launch 之后/会话创建之前装入 cave；host 映射记录页
  （`cuMemHostAlloc(DEVICEMAP)`）让 CPU 在 park 状态下直接读 trap 的 `ST.E`；
- **0317 陷阱里 `pbuf+0/+4/+8` 全部 0**（地址 `base−0x8000000`，可读不 fault；
  `R2=0x1` 而非 cmd=2 应得的 `0x30`）；launch trap 是 `0x8`；
- ⇒ 驱动在 agent 发起的 `0317{1,0}` 路径上**不写 pbuf**；cmd=2/idx 只属于真调试器
  suspend（cuda-gdb attach + target 注入）。0317 是通道级挂起 + 队列重放，
  不是 pbuf 命令 + CILP 原地恢复。
- 由此，**"handler 读驱动 pbuf 得到 request/target" 这条路关闭**；剩余路径仍是
  实现调试 agent，或换未关闭 regops 的平台。

## 9. 下一步优先级

1. **若目标是"尽快可用"**：维护 GDB backend，预热 cuda-gdb，把设备静止 116 ms 作为
   已知下限；不需要再碰 trap 恢复。
2. **若目标是"摆脱 cuda-gdb"**：实现/复用 `libcudadebugger` 进程内 agent
   （`DebugAgentMain` + `cudbgApi*` + preemption-buffer accessor）；这是唯一完整路径。
3. **若目标是"搞清因果"**：**sm86/570 的 A/B 已完成**（论文方法在其上跑通）；
   剩余的控制组是"595 装到 Ampere"和"GSP off"，需要能装驱动/改模块参数的机器。
4. **若目标是"论文复现"**：**已在 sm86/570 复现**（`level 3` p50 229 µs）；
   sm120 上用户态不可达；若必须 sm120，只能打开 `pGpu+0x911`（改驱动/注册表，超出
   安全边界）或实现调试 agent。
