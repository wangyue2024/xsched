# 02 路径与方法

> 本文把六条路线分别写清：想做什么、怎么做的、结果、还能不能用。
> 判定用语：✅ 可用 ｜ ⚠️ 有条件可用 ｜ ❌ 在当前平台不可行。

---

## R1. 带内寄存器触发（论文路线）— ✅ sm86/570 ／ ❌ sm120/595

**想法**：host 通过 ioctl 写 GPU 控制寄存器（`0x419e84` bit31），硬件立即 stall 运行中
kernel 并进入 trap handler；handler 通过 trap reason 识别"这是调度器请求"，abort 目标
kernel。这是 OSDI'25 Lv3 的做法。

**关键事实（本轮从 cuxtra 静态库逆出）**
- `cuXtraTriggerTrap` → `CudaKernelModule::GlobalRegsWrite32`
  → ioctl `0xc020462a`（`NV_ESC_RM_CONTROL`）+ cmd **`0x20800122`**（GPU_EXEC_REG_OPS）。
- 写入内容（`.rodata.cst16` 恢复）：对 `0x419e84` 打 bit31 脉冲：
  `{reg=0x419e84, value=0x80000000, mask=0x80000000}`，
  再来一次 `{value=0, mask=0x80000000}`。
- 该 control 的实现 `subdeviceCtrlCmdGpuExecRegOps_cmn@0x2dcfc0` 开头：
  `cmpb $0x0, 0x911(%gpu); je early_return`。
- `pGpu+0x911` 全二进制只有两处写，都在 `__nvoc_init_dataField_OBJGPU`（GPU init）：
  `0x17376 movb $0x1`、`0x17b4c movb $0x0`。运行期没有任何写点，RM 也没有控制命令能改。
- 因此 ioctl **返回成功但一个 op 都不执行**（`regStatus=0` 是假成功）。

**结论**：地址即使换成 sm120 的正确值也没用，**写入口被启动期闸门关死**——这是
**sm120/595 的结论**。同一路径在 **sm86/570 上是开放的**（上游 XSched 已跑通 `level 3`，
见文末 A/B）；A100/550 regops 也开放，但 sm80 不在上游 TarpHandler 支持列表。
除非改注册表/模块参数并重新初始化 GPU（rmmod/重启，超出安全边界）或换平台。

**证据**：`FINDINGS §v1.1`、`§32`、`RM_REVERSE §3`；`probe/regops.cpp`、`probe/rmstack.cu`。

## R2. CUDBGAPI（`cudbgApiInit/Attach`）— ❌（不是开关）

**想法**：cuda-gdb 用的 CUDA Debugger API 也许能在进程内直接初始化/attach，
绕过 gdb。

**事实**
- libcuda 导出 `cudbgApiInit(1|2)`、`cudbgApiAttach/Detach`、`cudbgGetAPI`，
  以及 BSS 开关 `cudbgUseExternalDebugger`、`cudbgEnablePreemptionDebugging`、
  `cudbgResumeForAttachDetach`、`cudbgEnableLaunchBlocking`。
- `cudbgApiInit(2)` 会遍历已存在上下文并检查 "late attach" 能力；错误串：
  "Late attach is not supported with CUDA MPS"、
  "Late attaching of a debugger that does not support CUDA lazy loading is not supported"。
- 它需要调试器注入机制（`CUDA_INJECTION64_PATH` / 进程内 agent / IPC），
  不是"设一个 flag 就打开 park"。

**结论**：`cudbgApiInit(2)` 失败不是参数问题；这条路的本质是"启动框架"，不是开关。
真正要做的是复刻 `libcudadebugger` 的 agent（见 P2）。

**证据**：`FINDINGS §16`、`§45`；`exp_cudbg*`。

## R3. 复刻 RM 调试器序列（0x83de）— ⚠️ 只能 park，不能恢复

**想法**：用外部 agent 建 0x83de 会话，发 0317/0318，复刻 cuda-gdb 的 suspend/resume。

**已打通的部分**
- **授权**：target 在 `NV01_ROOT` 上发 `0xd04 ClientSetInheritedSharePolicy`：
  ```c
  {target, 1, 0x0002} {target, 4, 0x40002} {agent, 1, 0x40003}
  ```
  之后 agent 可跨 client 建 0x83de 会话（否则 `0x1b`）。
- **会话**：`NVOS21 {hRoot=agentClient, hParent=device, hObject, hClass=0x83de,
  pAllocParms={hDebuggerClient=0, hAppClient=target, hClass3dObject=KGO}}`；
  `hDebuggerClient_deprecated` 必须为 0，KGO 必须是 0xcec0，会话挂在 kgrctx 的链上。
- **模式**：0301/0307/0309/031f/032a 等可接受；0301 不改变 park/cancel。
- **0317**：在受管上下文里，无调试器时要么 `0xffff`、要么阻塞；有 cuda-gdb 时返回 0
  但结果是 cancel；**在"init 前被外部 tracer 附着"的上下文里是真 park**（§42）。

**卡死的部分**
- park 之后 **0318 在 agent client 和 app 自己的 session 上都阻塞**（§30）。
- 写 preemption 命令字（+4=1）是恢复的必要条件，但用户态没有任何写入口（§37–§39、§43）。
- 命令字实际由 `libcudadebugger` 的 `IPreemptionBufferAccessor` 写（§45）。

**结论**：RM 路线能"停"，不能"自己恢复"；恢复必须由调试 agent 完成。

**证据**：`FINDINGS §v1.4、§17–§31、§40、§42`；`probe/l3agent.cpp`、`run_l3qspin.sh`。

## R3'. regops 直写寄存器 — ✅ sm86/570 ／ ❌ sm120/595

与 R1 同源：`0x83de031d`（DebugExecRegOps）和 `0x20800122` 都被 `pGpu+0x911`
早退；`gpuValidateRegOps` 只有在 flags 字节允许时才继续，但根本走不到那里。
`0x419e84`、`0x910/0x911` 这两个标志字是启动期固定的。

**证据**：`FINDINGS §v1.1`、`RM_REVERSE §3.1`、`probe/regops.cpp`。

## T. XSched trap backend（cave + 0317 + payload）— ✅ 停/杀/重放，⚠️ 不能原地恢复

**做法**
1. Init：定位活体 handler（10 条指纹），在 `+0x390` 写 `CALL.ABS` 到 slot-20 的 cave
   （`+0xA00`，8 条 SASS）。
2. cave 默认 benign return；需要抢占时改写为：
   - **kill**：把 trap return PC 指向 EXIT trampoline（payload 杀 warp）；
   - **reason probe**：记录 R2 / `c[0x170]`。
3. launch 走 shim → `XQueue::Submit`，队列记录 `last_kernel_`；
   resume 时重放被杀内核（idempotent）。
4. 触发：外部 agent 发 0317；设备在 0.2–27 ms 内停住。

**结果**
- standalone kill：8 s 内核 → **0.234 s**，结果正确；
- 受管 suspend：**27–30 ms**（cancel，stream 判完成），`0.204 ms` 真停住（预建会话）；
- kill+replay：resume 后新实例健康运行（7M→44M），done=1；
- 优缺点：不依赖 gdb 的"停"已成立；但"停住后可恢复"依赖驱动状态机，做不到。

**证据**：`FINDINGS §v2.0、§11–§15、§23、§33`；`platforms/cuda/hal/src/level3/trap_sm120.cpp`、
`probe/l3qspin.cu`、`run_l3qspin.sh`。

## G. GDB backend（交付形态）— ✅ 完整 park+resume

**做法**：外部进程 fork/exec `cuda-gdb`，attach 目标进程 → 设备 CILP save（116 ms）；
`detach` → restore。封成 `GdbInterruptContext::Suspend/Resume/Prepare(pid)`，
接入 XSched HAL 与 `l3ctl`。

**结果**（`tools/stability_test.sh` 三轮）
- 设备真正静止 **116 ms**（5 ms 采样单独测）；
- 真实 attach 开销 ~23 ms（`Prepare` 预热后；未预热时另有 ~0.3 s 的 gdb 启动）；
- 测试脚本口径：`Suspend()` 返回 0.52–0.54 s（其中含脚本自身 0.5 s sleep），
  租户完成 0.73–0.74 s；三轮抖动 < 3 ms，`Resume=1`。
- 中断后结果 bit-exact（v0.6）。

**限制**：依赖 cuda-gdb；attach 有 ~116 ms 物理下限；不能做到论文的 32 µs。

**证据**：`FINDINGS §v0.5–v1.3`；`platforms/cuda/hal/src/level3/gdb_interrupt.cpp`、
`run_l3hal.sh`、`run_l3handover.sh`、`test/main/l3ctl.cpp`。

## P. park-only（tracer + 0317）— ⚠️ 新证，只能停不能恢复

**做法**：在 CUDA init 前让目标进程处于外部 ptrace 下（`strace -f` 或 plain `gdb` 均可），
之后外部 agent 发 RM `0317`。

**结果**：内核**真 park**——采样线程持续打印但计数冻结 10–20 s，`Synchronize` 不返回；
agent 的 0317 可能阻塞或返回 `0xffff`。cuda-gdb 在场时它的 agent 会应答，变成 27.3 ms cancel。

**意义**：不需要 cuda-gdb 就能"停"，适用于"停住后不再恢复"的场景（驱逐/销毁/整进程回收）。
**不能**用于需要同 context 恢复的调度。

**证据**：`FINDINGS §42`；`exp_strace_park1/2.log`、`exp_plaingdb_park1.log`、
`exp_gdb_cancel1.log`。

## 路线对比（一图流）

```
             ┌── R1 带内寄存器 ──✅ sm86/570（上游跑通）／❌ sm120（pGpu+0x911）
             ├── R3' regops ─────✅ sm86/570 可读写寄存器／❌ sm120 同一闸门
触发/停住 ───┼── R3 RM 0317 ─────⚠️ cancel 或 park（park 不可释放）
             ├── T trap backend ─✅ cancel/kill 0.2–30 ms，可重放
             ├── G gdb backend ──✅ 116 ms 停、可恢复（交付）
             └── P park-only ────⚠️ 真停、不可恢复（需 init 前 tracer）

             ┌── 论文 handler 判据 ──❌ reason 不可区分 + 无入向通道
恢复 ────────┼── 用户态写命令字 ─────❌ pbuf 设备只读、CPU 零页
             ├── RM 0318 ───────────❌ 所有 client 阻塞
             └── 调试 agent ────────✅ 唯一入口（libcudadebugger）
```

## A/B 实测（2026-10-26）：R1 在 sm86 上成立

**做法**：在 RTX 3090（sm86/570）上按上游 `XpuOS/xsched`（commit `f49289f`）原样构建，
运行 `platforms/cuda/test/main/level.cu` 的 `level 3`。

**结果**
- `level 3`：preempt p50 **227–229 µs**，p99 310–2233 µs，restore 38–97 µs；
  dead-loop 内核也能停住并恢复（`TestDeadLoopPreempt` 正常退出）。
- `level 1`：p50 12.5–13.2 ms（等内核完成），restore 7 µs。
- 路径确认：sm86 → `CudaQueueLv3Trap`；`InterruptContext::InstrumentTrapHandler()`
  先 `TarpHandlerSM86::Instrument` 改写活体 handler，再 `cuXtraTriggerTrap(kCtx)`；
  触发写 `0x419e84` bit31（经 `0x20800122`）。
- **关键**：只写寄存器不插桩 handler 不够（A100 上我们只写寄存器，内核照跑）；
  **插桩 handler + cuxtra 触发** 才是论文的完整路径。

**判定**
- R1（带内触发）在 **sm86/570 上 ✅**；在 **sm120/595 上 ❌**（`pGpu+0x911` 关闭 regops）。
- 因此"Ampere vs Blackwell"不是主因；差别是 595 驱动的能力位策略。
- A100（sm80/550）regops 开放，但 sm80 不在上游 TarpHandler 支持列表（只 sm70/sm86），
  不能作为 sm86 实现的对照；它的 cuda-gdb 中断仍走 0317/0318。

证据：`../FINDINGS_ZH.md §49`、`../evidence/ab_ampere/logs/`。
