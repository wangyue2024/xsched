# 01 研究过程（v0.1 → v5.9）

> 每条都给出：阶段目标 → 做法 → 结论 → 证据位置。
> 详细论述见 `../FINDINGS_ZH.md` 对应章节；本文只保留主线。

---

## 第一阶段：证明"冻结/恢复"可行（v0.1–v1.0，2026-10-16）

| 版本 | 目标 / 做法 | 结论 | 证据 |
|---|---|---|---|
| v0.1 | 推翻 v1 的"平台判死"：在 libcuda 内嵌 plugin 里定位活体 trap handler | handler 镜像 `arena base+0x15f0f00`，10 条指纹可校验；`+0x390` 是安全 patch 点 | §1–§4 |
| v0.2 | 用 cuda-gdb attach 冻结运行中内核 | 冻结**确实发生**（不是假象）；v1 判死作废 | §1 |
| v0.3 | 复刻真实 cuda-gdb suspend 的 RM 配方 | 抓到完整 ioctl 序列；被 `RS_ACCESS_DEBUG` 挡住；首次发现 `pGpu+0x911` 闸门 | §1–§3 |
| v0.4 | 用外部调度进程驱动 attach/detach | **L3 中断闭环打通**：运行中内核可冻结/恢复 | §1 |
| v0.5 | 定型原语：`attach=冻结 / detach=恢复` | 不需要目标协作、不需要断点；设备静止 116 ms | §1 |
| v0.6 | 闭环验收 | 中断后结果 **bit-exact** | §1 |
| v0.7 | 更正 v0.5 的负面结论 | 冻结**确实让渡** GPU 资源 | §1 |
| v0.8 | agent 守护进程 + 控制块 | 外部 agent API 成型（后来的 `l3agent` 前身） | §1 |
| v0.9 | 接进 XSched HAL | **GDB backend 端到端 66×**（相对基线） | §1 |
| v1.0 | 用户形态 | `l3ctl` 命令行工具 | §1 |

**阶段结论**：`cuda-gdb attach/detach` 可以作为 L3 的"停/恢复"原语，代价是设备静止 116 ms；
这条路后来成为交付形态（`GdbInterruptContext`）。

## 第二阶段：带内触发/寄存器路径判死（v1.1–v1.3）

| 版本 | 目标 / 做法 | 结论 | 证据 |
|---|---|---|---|
| v1.1 | 打开 `pGpu+0x911`（regops 闸门） | 全二进制只有两处写该位，都在 `__nvoc_init_dataField_OBJGPU`（GPU init）；运行期无入口 → regops（`0x83de031d` / `0x20800122`）不可用 | §v1.1 |
| v1.1 | `cuXtraTriggerTrap`（`0x419e84` bit31） | 595/sm120 上送不进可用的 trap；不建立驱动 preempt 状态 | §v1.1 |
| v1.2 | 接控制面 | `xserver` + `xcli l3` | §v1.2 |
| v1.3 | 延迟剖析 | 106 ms 主要是设备 CILP save；gdb 进程启动可预热省掉 | §v1.3 |

**阶段结论**：论文式的"写寄存器 → 硬件中断"在 sm120/595 上被启动期能力位封死；
**唯一可用入口是调试器 attach**。

## 第三阶段：外部 agent 复刻调试器（v1.4–v2.4）

| 版本 | 目标 / 做法 | 结论 | 证据 |
|---|---|---|---|
| v1.4 | 打通 `RS_ACCESS_DEBUG` | 用 `0xd04 ClientSetInheritedSharePolicy` 把 target client 共享给 agent（黄金三条策略）；跨 client 建 0x83de 会话成功 | §v1.4 |
| v1.5 | 活体 handler 执行验证 | 注入载荷跑通（签名 0x5aa5），context 存活 | §v1.5 |
| v1.6 | park 控制面 | 能冻住；释放卡在 host 内存一致性 | §v1.6 |
| v1.7 | trap 上下文内存边界 | 全局读不通；改走 guardian kill | §v1.7 |
| v1.8 | L3 kill 闭环 | trap → 置 flag → guardian 退出 → context 存活 | §v1.8 |
| v1.9 | 读写语义 | trap 上下文**只能写、不能读**全局内存；改为按需改写 cave | §v1.9 |
| v2.0 | arm-by-patching | 预装 cave、运行期改写为 EXIT trampoline，实现 kill | §v2.0 |
| v2.1 | 接进 XSched HAL | 握手/授权/patch 全通，当时判定"卡在 launch trap"（**§18 更正**：是探针 `ST.E` 编码 bug，不是 launch trap） | §v2.1、§18 |
| v2.2 | 会话副作用 | 外部 0x83de 会话存在时，XSched 内核会被破坏 | §v2.2 |
| v2.3 | 运行期 arm | 会话存在时任何代码写都被驱动串行化（阻塞到内核结束） | §v2.3 |
| v2.4 | 复刻调试态 | 三次尝试均失败 | §v2.4 |

**阶段结论**：授权和注入没问题；**"运行期改代码"与"会话"互斥**，所以 cave 必须预装，
触发必须靠 0317；而 0317 的语义在受管上下文里不是 park。

## 第四阶段：受管上下文的 0317 语义与 kill+replay（§7–§31）

| 主题 | 做法 | 结论 | 证据 |
|---|---|---|---|
| §7 | cuda-gdb 在场/不在场对照 | 0317 无调试器时失败/阻塞；gdb 在场时返回、payload 可触发 | `exp_*` |
| §8–§11 | 让 launch 走 HAL 队列（shim） | 受管 launch + kill + replay 串通 | `exp_managed*` |
| §12–§15 | 无 payload 重放、合法 resume | resume 后新内核 ~3 ms 再停/700；`cuLaunchKernel` 等调试器 4.6 s | `exp_resume*` |
| §16 | `cudbgApiInit(2)` | 失败；late attach 有 MPS/lazy-loading 限制（见 §45） | `exp_cudbg*` |
| §17–§18 | 探针 bug 修正 | 首次抓到 reason=0x8（do_pause）；0317 在受管上下文必须有调试器 | `exp_probe_postresume.log` |
| §19 | 裸 l3x 对照 | 普通上下文 0317 能进 handler（reason=0x1），内核继续跑 | `exp_sig_rm0317.log` |
| §20–§21 | 命令字 park/restore、良性返回 | 不能原地恢复；resume 会重启内核但仍 ~3 ms 后 700 | `exp_cmdword*` |
| §22 | `run_l3qspin.sh` | 可复现实验台成型 | — |
| §23 | 受管上下文 0317 定性 | 是"取消在飞工作"，不是"暂停"（stream 判完成） | `exp_noinstr_cave.log` |
| §24 | 最小 InstrumentContext / `0317{0,0}` | 行为不变，排除 InstrumentContext 额外操作 | — |
| §25 | NvDebugAgent | 25 KB 薄启动器，协议在 stripped 的 libcudadebugger | `evidence/bin/NvDebugAgent` |
| §26–§28 | 二分 | `InstrMemAllocator` 决定 0317 语义；context 被标成调试器上下文 | `exp_direct_launch1.log` |
| §29 | 预 attach（l3mi） | 一次 attach/detach 后 0317 从 cancel 变 **park** | `exp_pre_attach1/2.log` |
| §30 | 自 session 发 0318 | 仍阻塞；park 无法从 app 侧释放 | `exp_self_resume1.log` |
| §31 | PTRACE_DETACH | ESRCH，park 不释放 | `exp_ptrace_detach1.log` |

**阶段结论**：受管上下文 + 0317 只有 **cancel** 或 **park 且不可释放** 两种结局；
差别由"context 是否处于 debugger-managed 状态"决定。

## 第五阶段：判据、延迟与通道边界（§32–§41）

| 主题 | 结论 | 证据 |
|---|---|---|
| §32 | handler 没有任何可用判据区分"抢占请求"与 launch trap；稳定配置里 reason 恒 0x1（§18 有一次 post-resume 0x8） | `exp_probe_plainlaunch.log`、`exp_cmdword_reason1.log` |
| §33 | 设备真正停住 **0.204 ms**（预建会话）；`Suspend` 返回 22.9 ms 是驱动 teardown | `exp_timeline1/2/3.log` |
| §34 | cave 必须保留 R1；驱动 trap 区域不能当通道 | `exp_table_probe*` |
| §35 | trap 上下文**数据读通路整体不通**（全局/UVA 恒 0；代码页/LDG fault）；写正常 | `exp_mem_probe2.log` 等 |
| §36 | handler 读的不是 XSched buffer，而是驱动 patch 的 pbuf（`base-0x2000000`）与 scratchpad（`base+0x1a00000`） | `exp_dump_read1.log` |
| §37 | pbuf 写路径：cuXtra 同步仅 Init、运行期 invalid、CUDA 异步 SIGSEGV | `exp_drvbuf_0/4/8.log` |
| §38 | 设备 kernel store 到 pbuf → Illegal Address | `exp_devcmd1.log` |
| §39 | trap 上下文对 pbuf 只读（ST 即 700） | `exp_drvbuf_rw*.log` |
| §40 | `0301 SMDebugModeEnable` 接受但不改变 park/cancel | `exp_smd0301*.log` |
| §41 | 读机制只在"轻上下文"可用；调试态下同地址 fault（疑重定位） | `exp_drvword_park.log` |

**阶段结论**：handler 的"输入协议"完全逆清，但**写入口只有驱动**；
用户态所有写路径都被封死。

## 第六阶段：打通路径定论（§42–§47，2026-10-26）

| 主题 | 做法 | 结论 | 证据 |
|---|---|---|---|
| §42 | 换 tracer：无 / `strace -f` / plain `gdb` / `cuda-gdb` | **外部 tracer 在 CUDA init 前存在 → 真 park**（计数冻结、`Synchronize` 不返回）；cuda-gdb 的 agent 应答 → cancel 27.3 ms | `exp_strace_park1/2.log`、`exp_plaingdb_park1.log`、`exp_gdb_cancel1.log` |
| §43 | park 后 `mprotect` pbuf 并读写 | mprotect 成功，但 CPU 读到零页、写入不可见（COW），内核仍 park | `exp_hostpoke_park1.log` |
| §44 | scratchpad host 写 + cave 读 | per-warp 记录 stride 0x2a0；+0x270/+0x300/+0x1000 均 700（即使关掉 host 写） | `exp_scratch_read_fault1/2.log` |
| §45 | 静态逆 libcuda/libcudadebugger/nv-kernel | 命令字由 `IPreemptionBufferAccessor` 写；0315/0316 只能访问 RM memobj；会话构造要求 `hDebuggerClient=0` 并绑定 kgrctx | 字符串/符号、`_nv83deCtrlCmdDebugAccessMemory@0x21a000` |
| §46 | 汇总通道与路径 | 完整 park+resume 唯一入口 = 进程内调试 agent；park-only 可用 | 本册 04/06 |
| §47 | 重读论文 | 论文的 flag 是 guardian 在普通上下文读的；handler 靠 **trap reason**；我们缺的是"可区分的带内中断源" | OSDI'25 §6.2–6.3、Fig.7/8 |

**最终结论**：论文式复现不可达；可用形态是 GDB backend（park+resume）与
park-only（tracer + 0317）。下一步是调试 agent 或换平台 A/B。

## 第七阶段：A/B 实测（2026-10-26）— 论文 L3 在 sm86/570 上跑通

| 项 | 内容 |
|---|---|
| 机器 | RTX 3090（sm86，570.124.04，GSP on，容器）；A100-PCIE-40GB（sm80，550.107.02）作对照 |
| 代码 | 上游 `XpuOS/xsched` main，commit `f49289f`（2026-08-19） |
| 构建 | CUDA 12.1 + g++11 + CMake 3.22；补 `3rdparty/cuxtra`、`3rdparty/ipc`（boost-ipc/tools）；`level` 用 `-arch=sm_86` |
| 结果 | **sm86 `level 3`：preempt p50 ≈ 229 µs、p99 ≈ 310–2233 µs、restore ≈ 90 µs；dead-loop 也能停**；`level 1` p50 ≈ 12.5–13.2 ms（等 kernel 完成） |
| 路径 | sm86 → `CudaQueueLv3Trap`；`InterruptContext::InstrumentTrapHandler()` 用 `TarpHandlerSM86::Instrument` 改 handler → `cuXtraTriggerTrap`（`0x419e84` bit31，经 `0x20800122`） |
| A100 | `0x20800122` 开放（可读 `0x200510`/`0x419e84`，写 bit31 返回 0），但 sm80 不在上游 TarpHandler 支持列表，且未插桩 handler → 内核照跑；cuda-gdb 中断仍走 0317/0318 |
| sm120 | `0x20800122` 被 `pGpu+0x911` 早退 → 只能 RM 0317（27 ms）/ GDB（116 ms） |
| 结论 | **论文方法可在 sm86/570 复现；sm120/595 的差别是 regops 能力位被关，不是 handler 机制本身** |

证据：`evidence/ab_ampere/logs/level1_sm86.log`、`level3_sm86.log`、`smi.txt`、`uname.txt`；
FINDINGS §49。
