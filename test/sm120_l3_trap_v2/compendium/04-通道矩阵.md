# 04 通道矩阵：host ↔ trap handler 的信息交互

> 目标：回答"能不能让 trap handler 和外部交换信息"。
> 结论先行：**出方向（trap → host）通；入方向（host → trap）在纯用户态不通。**
> 所有实验都在 `../evidence/live/` 有日志；方法学：用 64 位 sentinel 的高 32 位
> 是否保留来证明 cave 确实执行了，用 host 回读证明写入可见。

---

## 1. trap → host（出方向）✅

| # | 方法 | 结果 | 证据 |
|---|---|---|---|
| 1 | cave 里 `ST.E` 写用户全局内存（签名 0x5aa5） | ✅ host 回读 0x5aa5 | `exp_sig_*.log` |
| 2 | cave 写 host 映射 shm | ✅ | `exp_shm_*.log` |
| 3 | cave 写 scratchpad（per-warp 记录内） | ✅（驱动布局内） | `FINDINGS §40` |
| 4 | reason probe：cave 把 R2、`c[0x170]` 写到 `wr_buf+0x100` | ✅ +4 s 后 reader 打印 | `exp_probe_*.log` |
| 5 | ldg probe：额外记录 `LDG` 结果 | ✅（但值恒 0） | `exp_ldg_probe1.log` |

**限制**：只能"上报"；不能改变 handler 的决策。且写必须在 handler 的合法窗口内
（不能碰 R1/R12，不能写代码页除非用指令内存 API）。

## 2. host → trap（入方向）❌（逐条排除）

### 2.1 全局内存 / UVA

| # | 写入方式 | trap 读法 | 结果 | 证据 |
|---|---|---|---|---|
| 1 | host `cuXtraMemcpyHtoD` 写自己的 `cuMemAlloc` buffer | cave `LD.E` | **0**（sentinel 高 32 位保留，证明 cave 执行） | `exp_mem_probe2.log` |
| 2 | XSched preempt buffer（`c[0x170]` 指针），Deactivate 写 1 | cave `LD.E` | **0** | `exp_flag_probe1.log` |
| 3 | flag=1 时读同一 buffer | cave `LD.E` | **700** | `exp_flag_probe2.log` |
| 4 | `cuMemHostAlloc(DEVICEMAP)`，host VA==device VA | cave `LD.E` | **0** | `exp_uva_probe1.log` |
| 5 | handler 自己的代码页（已知内容） | cave `LD.E` | **700** | `exp_code_probe1.log` |
| 6 | 描述符式 `LDG.E`（`LDCU UR4,c[0x358]`） | `LDG.E.64 desc[UR4]` | **700** | `exp_ldg_probe1.log` |
| 7 | 同一 buffer 改用 `LD.E.CONSTANT` | `.CONSTANT` | **0** | `exp_const_probe*.log` |
| 8 | 读 `trap_reason_table`（host 可读写） | cave `LD.E` | 0 / 不可用；写它会破坏驱动 trap → 下次 700 | `FINDINGS §34` |

**结论**：不是 cache、不是分配方式、不是 0/非 0 —— trap 上下文的**数据读通路整体不通**。
因此"host 写 flag、handler 读"的论文式软件 mailbox 不存在。

### 2.2 驱动 preemption buffer（handler 真正读的那块）

| # | 写入方式 | 结果 | 证据 |
|---|---|---|---|
| 1 | `cuXtraMemcpyHtoD(pbuf+4)`，**Init（无内核）** | `w=4`，回读 0x2 —— 但只是 cuxtra 自己的路径，不能证明对 trap 有效 | `FINDINGS §37` |
| 2 | 同上，**运行期（Trigger）** | `cuda error 1 (invalid argument)` | `exp_drvbuf_0.log` |
| 3 | `cuMemcpyHtoDAsync_v2_ptsz` + StreamQuery，运行期 | **libcuda 内 SIGSEGV** | `exp_drvbuf_4.log` |
| 4 | `CuMemcpyDtoH` | `r=1 invalid value` | `exp_drvbuf_8.log` |
| 5 | 设备 kernel store（`l3write` PTX） | **Warp Illegal Address** | `exp_devcmd1.log` |
| 6 | trap 上下文 `ST.E [pbuf+4]` | **700**（只读映射） | `exp_drvbuf_rw*.log` |
| 7 | park 后 `mprotect(pbuf 页, RW)` + CPU 读写 | mprotect 成功；读 `+0/+4/+8` 全 0；写 1 回读 1；内核仍 park（COW 零页） | `exp_hostpoke_park1.log` |
| 8 | **cave 在 0317 trap 里直接读** `pbuf+0/+4/+8`（arm-at-Trigger） | **可读、不 fault，但三个字全 0** —— 0317 路径驱动不写 | `exp_arm_pbuf_{cmd4,idx8,flag0}.log` |

**结论**：pbuf 只在设备/trap 地址空间；CPU 侧是 PROT_NONE 占位；用户态 host/device
都写不到。唯一写它的是驱动/调试 agent。**更重要的是：agent 发的 `0317{1,0}` 本身
也不写 `+4/+8`**（§52：`R2=0x1` 而非 cmd=2 应得的 `0x30`，且 do_read 先读也为 0），
所以它连"读取驱动写的 request/target"这条路也走不通。

### 2.3 scratchpad（唯一 host rw-s + trap 可见）

| 实验 | 结果 |
|---|---|
| host 通过 `/dev/nvidiactl` rw-s 映射写 sentinel 到 `scratch+0x1000 / +0x300 / +0x270`，cave `.CONSTANT` 读同址 | **launch trap 700** |
| 关掉 host 写，只读 `+0x270` | **仍然 700** |
| 布局 | per-warp 记录 stride **0x2a0**；字段 `+0x290/+0x294/+0x298/+0x29d/+0x29e` |
| 判定 | trap 可见窗口只覆盖活动 warp 记录；盲访不安全；没有证据表明存在"请求"字段 |

证据：`exp_scratch_read_fault1/2.log`、`FINDINGS §44`。

### 2.4 RM 内存访问（0315/0316）

- 参数 `{hMemory, size, offset, hostbuf}`，实现里有 `offset+size <= memdesc.size` 边界检查；
- 只能访问 **RM Memory 对象**；pbuf 不是 RM memobj（不在任何 client 的句柄空间）；
- 因此 0315/0316 **到不了** pbuf；可以用来读写普通设备内存，但那本来就通。

证据：`_nv83deCtrlCmdDebugAccessMemory@0x21a000`、`FINDINGS §45`。

## 3. 为什么入方向必须由驱动/agent 完成

```
host 写请求位 ──✗──> 普通全局内存（trap 读=0）
             ──✗──> XSched preempt buffer（trap 读=0 或 700）
             ──✗──> 驱动 pbuf（设备只读 / CPU 零页 / 设备 store 非法）
             ──✗──> scratchpad（驱动 per-warp 布局，盲访 700）
             ──✓──> 驱动自己（调试 agent 写 pbuf+4） ← 唯一路径
```

驱动 preemption buffer 的写入是**调试器 suspend/resume 状态机**的一部分：
- **真调试器 suspend**（cuda-gdb attach + target 侧注入）→ 驱动/GSP 写 `+4=2`，
  handler do_preempt_save + do_pause；
- **agent 直发 `0317{1,0}`**（本机实测）→ handler 收到 `reason=0x1`，但 pbuf 三字全 0，
  没有 cmd=2/idx ⇒ 只是通道级挂起，不做 CILP 保存；
- 0318/continue → 调试 agent 写 `+4=1`，handler restore；
- 没有 agent 时，0317 要么 cancel，要么 park 且无人写 1（`0318` 在所有 client 阻塞）。

## 4. 对照原论文（重要更正）

论文的"信息交互"不是 host↔handler mailbox：

1. **Lv2 guardian（Fig. 7/8）**：per-hwQueue flag 在 **GPU global memory**，
   地址由 kernel 参数/constant memory 传入，**由注入到 kernel 的 guardian 读取**
   （普通 kernel 上下文）；abort 记录也由 guardian 写回全局内存，host 重放。
2. **Lv3 queue-based（§6.3）**：host 用 ioctl 写 GPU 控制寄存器 → 硬件 stall →
   trap handler **检查 trap reason**；XSched 扩展 handler 识别自己的中断并 abort 目标
   kernel，其余 restore 继续。
3. 论文**不需要** host→handler 数据 buffer，也**不要求** handler 读全局内存。
4. 恢复：论文明确不支持断点恢复，只对 idempotent kernel 从头重跑。

**我们的差距**：
- **reason 其实可区分**（§52 实测）：0317 陷阱 `0x1`，launch trap `0x8`——足以让 payload
  只对 0317 动作；但 0317 **没有 request/target 数据**（pbuf 全 0），只能做"全体 EXIT"，
  不能做选择性 abort；
- 缺"驱动不参与"的带内中断源（regops 被 `pGpu+0x911` 关）；
- 因此只能沿用驱动的命令字协议，而写它需要调试 agent。

## 5. 如果一定要做 mailbox，还缺什么

| 需求 | 现状 | 可行路径 |
|---|---|---|
| host→handler 的可读地址 | 普通内存读=0；pbuf 只读；scratchpad 窗口未知 | 逆完 scratchpad 布局，找驱动不用的槽位并验证生命周期（未证明存在） |
| handler→host 的应答 | ✅ 已通（写全局内存） | 已有 |
| 触发/区分 | 0317=`0x1`、launch=`0x8`（**可区分**）；但无 request/target 数据 | 需要带内中断源（换平台/开 regops）或接受调试 agent 协议 |
| 恢复 | 0318 阻塞 | 调试 agent 写 pbuf+4=1 |

**结论**：完整双向 mailbox 在当前平台**没有用户态实现**；唯一接近的是 scratchpad，
但它属于驱动私有布局，风险高、未证明。

## 6. A/B 实测补充（2026-10-26）

- **sm86/570**：上游 XSched 的 `TarpHandlerSM86::Instrument` + `cuXtraTriggerTrap`
  跑通论文 L3（preempt p50 ≈ 229 µs、restore ≈ 90 µs）。
  这说明论文的"信息交互"不是 host→handler mailbox，而是：
  **寄存器写触发 + 插桩后的 handler 按 trap reason 决定 abort**。
- **只写寄存器不够**：A100 上我们只做 `0x20800122` 写 `0x419e84` bit31（未插桩
  handler），内核照跑；必须先把 handler 改写（TarpHandlerSM86）再触发。
- **sm120/595**：同一条寄存器写路径被 `pGpu+0x911` 早退，无法触发；
  只能 RM 0317（debugger-suspend）→ 27 ms cancel/park，或 GDB backend → 116 ms。
- A100（sm80/550）regops 开放，但 sm80 不在上游 TarpHandler 支持列表
  （只 sm70/sm86），不能作为 sm86 实现的对照；它的 cuda-gdb 中断仍走 0317/0318。

证据：`../FINDINGS_ZH.md §49`、`../evidence/ab_ampere/logs/`。
